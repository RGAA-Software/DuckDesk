# Protobuf 协议演进规范

## 1. 目的与适用范围

本文规定 GammaRay/Pixels 项目中 `.proto` 文件的兼容性要求，适用于 C++、Rust、TypeScript/Web、Android 及其他由同一协议生成或手写适配的消费者。

修改 `.proto` 并不必然导致兼容问题。只要遵守追加式演进、永久保留既有编号并完成跨版本验证，新旧端可以安全混合运行。任何修改都必须同时考虑二进制 Wire Format、生成 API 和业务语义三层兼容性。

## 2. 项目强制规则

1. 已发布字段号永久固定，不得修改，也不得分配给其他字段。
2. 已发布枚举数值永久固定，不得修改、重排或复用。
3. 新字段必须使用从未使用过的新字段号；新枚举项必须使用从未使用过的新数值。
4. 删除字段或枚举项时必须先弃用，并在 `.proto` 中 `reserved` 原名称和编号，禁止以后复用。
5. 不直接修改既有字段类型。即使两种类型使用相同 Wire Type，也可能出现符号、范围、UTF-8、默认值或业务语义差异；需要变更时新增字段并执行显式迁移。
6. 不改变既有字段的 `oneof` 归属、存在性语义、单位、含义或权限语义。需要新语义时新增字段或消息版本。
7. 消息包名、消息名和字段名的重命名虽然可能保持部分二进制兼容，但会影响生成 API、JSON 名称、反射、`Any`、protobufjs 和手写 Web 适配，因此必须按跨端协议变更处理。
8. 所有协议消费者必须由同一权威 `.proto` 重新生成。禁止复制十进制消息号到业务代码；需要轻量分类时使用生成枚举或由构建系统生成的枚举视图。
9. Render、Client 及承载 Protobuf 对象布局的内部库必须作为同一协议兼容单元构建和发布，不得混用不同生成版本的二进制产物。

## 3. 常见修改的兼容性

| 修改 | 二进制兼容性 | 项目要求 |
|---|---|---|
| 增加使用新编号的可选字段 | 通常兼容 | 旧端忽略未知字段；新端必须正确处理字段缺失 |
| 增加使用新数值的枚举项 | Wire 层兼容 | 所有读取方必须有未知枚举处理，不能把未知值静默解释成合法默认行为 |
| 增加新消息类型 | 通常兼容 | 未声明能力的旧端不得收到该消息；通过能力协商或版本门控启用 |
| 调整字段声明顺序 | 兼容 | 字段顺序不是协议身份，不能依赖序列化顺序 |
| 重命名字段但保留编号 | 二进制通常兼容 | JSON、反射和生成 API 可能不兼容，项目内按协调变更处理 |
| 删除字段并保留编号 | Wire 层可兼容 | 先弃用，确认业务允许缺失，然后 `reserved` 名称和编号 |
| 修改或复用字段号 | 不兼容 | 禁止 |
| 修改或复用枚举数值 | 不兼容或产生错误语义 | 禁止 |
| 修改字段类型 | 可能不兼容或静默误读 | 禁止原地修改；新增字段迁移 |
| 改变 `oneof`、默认行为、单位或权限语义 | 业务不兼容 | 新增版本化字段或消息，并完成能力协商 |

## 4. `Message.type` 与 TCP 媒体丢弃边界

`px.Message.type` 是网络路由和拥塞策略的关键协议字段。它的字段号以及 `kVideoFrame`、`kAudioFrame`、`kVoiceAudioFrame` 的枚举数值属于永久协议身份，不得修改或复用。

TCP/WebSocket 拥塞时，项目只允许丢弃以下实时媒体：

- `kVideoFrame`
- `kAudioFrame`
- `kVoiceAudioFrame`

键鼠输入、控制、心跳、剪贴板、文件传输、RDP、会话管理和其他消息不得进入可丢弃媒体预算。

`src/px_render/network/ws/ws_realtime_media_queue.cpp` 为避免解析和复制整块高码率媒体负载，只扫描 Protobuf 消息头中的 `type` 字段：

- 字段号直接使用生成代码中的 `Message::kTypeFieldNumber`。
- 消息类型数值直接使用生成的 `MessageType` 枚举。
- Wire Type 使用 Protobuf 规范定义的强类型枚举；其数值属于稳定的 Wire Format 标准，不是业务消息编号。
- 扫描支持字段乱序并跳过已知 Wire Type 的未知字段，不依赖当前序列化字段顺序。
- 缺少 `type`、格式损坏、遇到不支持的编码或无法识别类型时，一律分类为非媒体并走可靠路径。失败保护必须优先保证“不误丢非媒体数据”。

普通的 Protobuf 库升级、增加字段或调整字段声明顺序不会破坏该分类器。原地修改 `Message.type` 的字段类型属于禁止的破坏性变更；修改字段号即使重新生成当前端代码，也会破坏与旧端的混合版本通信，因此同样禁止。

## 5. 修改流程与验收门禁

修改任何已在网络中使用的 `.proto` 前后必须完成以下检查：

1. 确认所有现存字段号和枚举数值保持不变；检查被删除编号是否已 `reserved`。
2. 重新生成所有相关语言和平台的协议代码，不手工编辑生成文件。
3. 检查 C++、Rust、TypeScript/Web 和 Android 是否存在手写数字、独立枚举或动态反射名称，并同步修正。
4. 对新增字段验证“旧端读取新消息”和“新端读取旧消息”；新字段缺失时必须具有安全、明确的行为。
5. 对新增枚举值验证未知值路径，不允许落入具有权限、控制或破坏性含义的默认分支。
6. 对新消息类型增加能力协商或版本门控，禁止无条件发送给旧端。
7. 运行协议往返、跨版本、畸形输入和未知字段测试。
8. 修改 `px.Message` 时必须运行 `test_ws_realtime_media_queue`；测试应遍历生成的全部 `MessageType`，确认只有三种音视频帧可进入丢弃路径。
9. 将使用同一 Protobuf 生成布局的运行时产物原子发布，并验证构建目录与 `build_official/dist` 中对应文件的 SHA-256 一致。

## 6. 破坏性变更的正确做法

确实需要改变既有语义时，不在原字段上修改：

1. 使用新字段号或新消息类型表达新语义。
2. 为新能力增加显式协商或协议版本门。
3. 在过渡期同时支持旧字段读取和新字段读取，但只保留一个权威写入策略。
4. 完成所有受支持版本迁移后停止写旧字段，将其标记为 deprecated。
5. 最终移除时 `reserved` 旧字段名和编号；不得复用。

如果产品决定不兼容旧版本，也必须显式提升协议版本并在连接前拒绝不匹配版本，不能依赖解析失败、默认零值或运行中异常来区分版本。
