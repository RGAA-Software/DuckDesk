# Native UDP 媒体 v2 字节合同

本文是 Native UDP 媒体 v2 的当前权威协议说明。仅替换下行音视频；关联、心跳、恢复请求、语音及 WS 不变。不支持旧媒体格式回退；两端必须一起部署。

固定参考版本：Sunshine `3cba9baebac882b336be3ebe129ee612cb189853`；配套 `moonlight-common-c`
`e41355ea01670fd4c830b384009d31dd0339a705`；配套 nanors `b1e3c22ca0cdc0bb83e3cd6ed1a2fc77869ed99a`。
参考源位于 `D:/source/Sunshine`，只读使用；项目维护的 Windows 批量 UDP 适配按 GPL-3.0 保留来源和许可清单。

## Pixels 适配层

所有下行媒体数据报以 8 字节头开始：`50 58 4d 02`、媒体类型（1 视频 / 2 音频）、流槽（音频必须 0）、两个保留零字节。
完整数据报最大采用现有 `udp_mtu`（576–1500），不是内层包另加 8 字节。

### 路径分档与 `1500` 接收容量

- Client 参考 Moonlight 的成熟策略按当前路由选择**完整 UDP payload** 大小，该值包含 8 字节 Pixels 媒体头，不包含 UDP/IP 头：
  局域网 `1400`，远程 IPv4/VPN `1040`，远程 IPv6/未知路径 `1200`。
- Client 在 UDP Hello 中强制携带选择结果；Render 的 `udp_mtu` 是服务端上限，实际发送值为客户端选择值与服务端上限的较小者。
  UDP 控制协议版本为 2，不兼容缺少包长字段的旧 Hello，Client 与 Render 必须成对升级。
- Client 创建 UDP socket 时使用的 `1500` 是**用户态单次接收容量和 Pixels 协议上限**，不是向网络发送 1500 字节包，也不代表路径 MTU。
  它用于避免 asio2 默认 1024 字节缓冲截断首包，并允许接收协议范围内的任意服务端受限值。
- `1400` 只用于确认是非 VPN、MTU 不低于 1500 且目标在链路上的局域网路径。Windows 通过系统最佳路由和出接口判断；无法判断时必须使用 `1200`，不能乐观按局域网处理。
- 协议的 `576..1500` 是输入校验范围，不等于其中每个值都能在任意网络上无分片传输。未知公网路径的后续正确演进是从保守基线开始，
  用 DPLPMTUD 探测后升到 1400；不是把接收缓冲的 `1500` 当成发送 MTU。

视频内层为上游未加密 RTP/NV 格式：32 字节包头，分块 RS 最大 255 分片、最多 4 块，8 字节短帧头；超过四块按上游规则关闭该帧 FEC。
不支持 10 位分片索引溢出；与上游仅报错继续不同，本实现拒绝这种帧。

视频编码数据前增加受 FEC 保护的 28 字节描述符，以下多字节字段均为大端：

| 偏移 | 字段 |
|---|---|
| 0–2 | `50 56 02` |
| 3 | 编码类型：1 H264 / 2 H265 |
| 4 | 流槽，必须与外层一致 |
| 5 | UTF-8 屏幕名长度（0–255 字节） |
| 6、8 | 宽、高，各 16 位 |
| 10–11 | 保留零 |
| 12 | 原编码器帧号，64 位 |
| 20 | 编码数据长度，32 位 |
| 24 | 独立传输帧号，32 位，与 RTP 帧号一致 |
| 28 起 | 屏幕名，然后编码数据 |

RTP 视频帧号是每流从 1 开始的独立连续计数，不使用可能跳号的采集/编码器时间戳。包序号是每流 16 位连续序号，RTP 时间戳为单调 90 kHz。
丢帧恢复从最后完整交付的编码器时间戳之后开始失效；首次 IDR 前不为加入连接之前的帧发送 RFI。编码器不能安全失效该范围时使用现有 IDR 回退。
短帧头末包有效长度用于去掉零填充。重建包必须按原版接收器补回校验生成后填写的头字段，不能把这些字段的 RS 结果直接使用。
参考链仅在完整帧实际交付后推进；首帧必须 IDR。确认恢复帧的标志只能来自编码器输出，不来自网络收到请求。

音频内层保持上游 RTP 12 字节头，数据类型 97、校验类型 127；校验包再包含原版 12 字节 FEC 头。
每 4 个数据包发 2 个校验包，使用原版专用 4＋2 矩阵。包序号 16 位，时间戳按每包 20 ms 增长（不是 48 kHz 采样数）。
Pixels 保护负载是 `16 位大端 Opus 长度 + Opus + 零填充`，固定长度 `udp_mtu - 32`。因此数据包比 MTU 少 12 字节，校验包正好等于 MTU。
这是适配现有变长 Opus、且不更改采集/RTC 的明确差异，不宣称与原版 Opus 裸负载相同。长度字段也受 RS 保护，解码前剥离。
Opus 继续 48 kHz、双声道、20 ms / 960 samples；本轮不改为 Sunshine 默认 5 ms，也不承诺相同音频恢复时延。

## 接收与发送差异边界

- 音频顺序包即时交付，首个不完整保护组跳过；乱序、下一组触发放弃、PLC 行为用原版 `RtpAudioQueue.c` 做差分。
- 固定版本的音频乱序超时表达式为 `20 * 4 + 10000` 微秒，按其原表达式保留并记录，而非无记录修正单位。
- 音频最多保留 64 组；非法/不一致参数拒绝，不禁用 FEC 后旁路。视频帧比较使用完整 32 位回绕语义。
- 新路径停用旧 5 秒动态冗余，只保留固定配置及统计；恢复请求数量不是丢帧率。
- Windows 视频发送在 socket 所属线程优先尝试上游每消息 UDP 分段批量发送；单包或不支持时逐包回退。
  每批完成后才推进生产端，不把异步排队当成发送完成。
- 原产品发送预算为 80 Mbps / 最多 10 包一批，并非原版 800 Mbps / 64 KiB 参数；内外层和 FEC 字节均计入 pacing。
  2026-09-11 的未验收调试版本暂用 16 Mbps / 不超过 1 ms 字节预算一批，对照结果见 `windows_udp_stability_20260911.md`。
  此临时值已由 2026-09-11 收尾实现替换：按应用总码率扣除固定长度音频 FEC 的实际线速预留，再为视频计算编码与发送预算。
  1400 字节、8 Mbps、20% FEC 对应视频编码 5208800 bit/s、视频线上预算 7136000 bit/s。
- 最多一批视频发送在途，等待超过 100 ms 放弃该帧后续包；上一批未完成时不继续堆积新批。恢复由现有 RFI / IDR 入口处理。
- 这些是算法接入合同，不是性能或真实客户端验收结论；实际结果另写验收记录。
