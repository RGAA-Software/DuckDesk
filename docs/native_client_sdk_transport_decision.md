# 原生客户端 SDK 与 WebRTC 产品边界

> 决定日期：2026-09-07
> 状态：已开始实施；SDK 目录与构建接入迁移已完成双端编译与 Windows 冒烟验证；传输退役与核心/平台分层仍待实施。
> 本文替代此前原生客户端支持 WebRTC、Windows 保留 host 直连，以及原生 WS 媒体/Direct/Relay 多传输选择的规划。
> 归档规则：本次精简的原有代码放入根目录 `backup/`，不直接删除。下文“删除/移除”均指退出活动源码与构建依赖，原实现须先完整归档。

## 1. 最终决定

- 原生客户端目标平台为 Windows、Android、iOS、macOS；iOS 与 macOS 平台适配列为后续工作。所有原生客户端均不支持 WebRTC，包括 host 直连、NAT 穿透与 TURN 中继模式。
- WebRTC 仅用于 Web 客户端；保留浏览器使用的 Render RTC、信令、鉴权、ICE/TURN 和部署能力。
- 原生客户端当前只有一种连接组合：UDP Direct + FEC 媒体，以及 WebSocket 可靠控制/文件通道。WS/WSS 是同一通道的安全配置，不是两种产品连接模式。
- 原生客户端当前不支持公网 P2P、Relay、WebRTC、独立 WS 媒体模式或旧 UDP/KCP 备选模式；后续公网连接按 RustDesk 方案另行设计。
- UDP 媒体建立失败时明确报告不可达并允许重试，不再自动切为 WS 视频、RTC 或 Relay。允许文件独立使用可靠通道，不要求先建立视频。
- 这是基于用户验证和产品方向作出的决定，不再以增加 WebRTC 对比测试作为落实前置条件。
- 既有 RTC、原生 Relay 和 WS 媒体回退验收记录保留作历史证据，不再作为原生客户端后续功能开发或发布门禁。

## 1.1 通道职责

| 通道 | 职责 |
|---|---|
| UDP 媒体 | 编码视频分片、FEC 恢复、实时音频与必要媒体反馈；按时效丢弃过期帧 |
| 控制 WebSocket | 会话认证、UDP 端点关联、键鼠/手柄可靠事件、配置、心跳、剪贴板元数据、语音同意/挂断 |
| WebSocket 文件消息 | 文件上传/下载、目录、文件型剪贴板数据、取消/重试；保留现有背压与任务调度 |

这些职责属于同一逻辑会话，不是可选传输模式。普通 UDP 会话的文件消息继续复用已认证控制 WebSocket，独立文件模式沿用现有文件连接；
本轮不强制新建独立文件连接或改动一次性票据兑换流程。媒体中断不伪造账号离线或控制权变化；文件任务的存在不等于视频已经连接。
当前代码的视频已有 Reed-Solomon FEC，UDP 音频已有 jitter buffer/Opus PLC；不能将它表述为所有音频已实现同样的 FEC。
语音实时数据按统一媒体边界适配，同意/挂断保留在可靠控制面；现有语音路径的迁移需核对后实施，不标记为已完成。

### 1.2 客户端设置与连接入口

- Windows、Android、iOS、macOS 不提供手动或强制选择通道的能力；设置页、设备连接偏好、连接弹窗、远控工具栏和高级/调试设置均遵守此规则。
- 归档“强制 UDP/WS/RTC/Relay”“优先某协议”“自动选择通道”及“允许媒体回退”等选项和专属实现，不通过隐藏入口继续提供。
- 原生 SDK 固定使用 UDP+FEC 媒体与 WebSocket 控制/文件组合，UI 只提供连接、重试和结束会话；UDP 不可达时显示明确错误及网络诊断。
- 清理旧设置读写和 Panel 启动时的强制通道参数透传；旧持久化值不得再改变连接方式，不新增旧设置兼容层。
- 地址/端口等必要接入信息，以及实际生效的画质、音频、输入、解码偏好仍可配置；诊断可只读展示媒体/控制状态，不提供切换动作。
- Web 客户端固定使用既有 WebRTC 路径，本条不要求重做 Web 页面或扩展功能。

## 2. SDK 目标

Windows、Android、iOS、macOS 复用同一 C++ 会话、协议与媒体任务核心，分别注入平台解码、显示、音频、文件授权与生命周期适配。
公共核心不依赖 Qt UI、Android API 或 RTC 传输实现。Windows 不再作为 WebRTC 特例接入公共 SDK；各原生端不暴露协议选择器或多传输降级状态机。

- 传输与编码分离：原生链路传递项目媒体消息，不受 WebRTC RTP codec 列表约束。
- codec、profile、像素格式、输出尺寸等仍受两端真实编码/解码能力限制；移除 RTC 不能被表述为自动支持所有编码。
- 会话身份、票据使用/续发、重连、取消、超时、输入、文件任务、剪贴板传输与语音同意规则收敛到共享核心。
- 编码帧录制复用 `px_media_record`，文件传输复用 `px_ft_engine`，原生语音复用可适配的 Opus/音频端点。
- iOS 后续补充 Objective-C++/Swift 桥接和 Apple 平台适配，不再建设第三套 RTC 会话、信令、音轨与录制实现。
- 完整跨平台视频能力协商仍按此前决定暂缓；当前入口必须保留真实支持范围校验。

### 2.1 SDK 独立目录（已完成第一检查点）

将 `src/px_deps/px_client_sdk` 抽离为 `src/px_client_sdk`，与 `px_client`、`px_android`、`px_render` 同级，作为项目维护的正式模块。
这是现有 SDK 的迁移与依赖整理，复用已完成的 UDP/FEC、WebSocket 和媒体实现，不重新开发传输通道。

- 迁移前按归档规则保存原 SDK 的完整内容，包括未提交改动；迁移后的活动源码只保留在 `src/px_client_sdk`。
- 原路径不保留可编译副本、转发 CMake、符号链接或兼容头；`backup/` 内原版不参与构建。
- 同步修改根工程与 Android native 的 CMake 接入、SDK 内部相对依赖、调用方 include 路径、测试、`build_cpp_*.bat` 相关脚本和维护工具。
- SDK 使用自身明确的源码根目录与 target 级 include/link 声明，不再通过 `PX_PROJECT_PATH/px_client_sdk` 假定 SDK 位于依赖目录。
- 目录迁移阶段可以保留现有 `px_sdk` 构建目标名；公共接口和平台适配整理独立验证，不以表面改名扩大改造范围。
- `px_common`、`px_message`、`px_ft_engine`、`px_media_record`、`px_voice_call` 等共享依赖本次不随目录搬迁而整体移动或复制；
  SDK 通过明确构建目标复用它们，后续根据实际责任边界整理。
- 验证 Windows、Android 均从新目录构建同一套 SDK，活动构建和维护入口不再引用旧源码路径；历史记录和归档清单可保留旧路径。
- 2026-09-07 已迁移到 `src/px_client_sdk`；旧 SDK 和接入代码完整保存在归档批次，`manifest.json` 记录 1,305 个源文件及 SHA-256。
- `px_sdk` 通过 target 级公开 include 目录供两端消费；移除根工程和 Android 对旧 SDK include 目录的假定。
- 目录迁移保持原有运行行为；尚不能据此宣称 RTC/Relay 已退出、Qt 已从核心解耦或 iOS/macOS 已可构建。

### 2.2 macOS 客户端（已规划，后续适配）

- macOS 定位为原生观看与控制客户端，复用 `src/px_client_sdk` 的 UDP+FEC、WebSocket 控制/文件、会话、输入协议、录制与语音核心。
- 后续适配 macOS 的解码/显示、音频设备、键鼠/手柄输入、剪贴板、文件访问、凭据存储和应用生命周期；不重新实现传输协议。
- 适合共用的 Apple 平台底层代码可与 iOS 共用，桌面窗口/输入/权限和生命周期保持各自适配，不把 macOS 当作 iOS 分支处理。
- SDK 本轮分层须允许独立 Apple 平台适配，不以“非 Android 就是 Windows”选择依赖；不提前新增空适配器或占位实现。
- macOS UI 技术选型、最低系统版本、CPU 架构范围、构建/签名/分发方式和实机验收在正式启动适配时确定。
- 当前不创建 macOS 应用工程、不承诺已有 macOS 构建或功能通过；本轮仍聚焦 Windows/Android 接入与 SDK 精简。

## 3. 实施范围

### 原代码归档

归档目录使用 `backup/native_transport_simplification/<原仓库相对路径>`，保留源码、相关测试和配置的对应关系。
完整退役文件原样归档；仍要维护的混合文件在清理旧分支前保存完整原始版本，包括未提交内容。清单记录来源路径、基础提交、
本地修改状态及退出原因。已有归档不覆盖，重复归档使用新批次。`backup/` 不参与编译、测试扫描、发布打包或运行加载，
不作为兼容实现继续维护；仍被 Native/Web 消费的共享实现继续留在活动代码中。

### Android

删除 WebRTC AAR、专属信令/PeerConnection/统计、RTC 录制与语音控制器、RTC 文件/剪贴板 JNI 桥接、对应入口和孤立测试。
移除原生 Relay、WS 视频回退、旧 UDP/KCP 路由与对应专属配置；保留 UDP+FEC 和可靠控制/文件通道。
保留原生文件、剪贴板、录制、语音实现，保留账号、应用、票据与安全校验。删依赖后同步核对许可证和发布归档要求。
账号与应用目录可以继续使用 Console；它只提供授权与目标信息，客户端连接实际可达的 Render 端点。没有直达条件时明确失败，不引入中继。

### Windows 与 Panel

移除原生客户端的 `kWebRtc`、`kWebRtcDirect`、`kRelay`、旧 UDP/KCP 和 WS 媒体选择/构建/运行分支；同步修改 Panel 启动参数、自动选择、
配置入口和测试。取消 Client 对 RTC 传输 DLL 的链接与独立客户端包装，不改动 Web/Render 使用的库或既有第三方 ABI 所有权。
语音 APM 等可能复用 libwebrtc 算法的非传输依赖须单独核对消费者与替代边界，不能因删除 RTC 传输而误删语音处理功能。

### Render、Console 与 Web

保留 Web 所需的 RTC Local/Remote 服务、信令、票据兑换、ICE/TURN 与客户端资源。原生客户端启动策略不能再选择 RTC；
Web 的启动策略继续允许 RTC；它使用的信令 Relay/TURN 不受原生 Relay 退出影响。原生专属服务端入口按实际消费者清理，不能误删 Web 依赖。
共用协议的旧枚举编号不得重排或复用，不为退役原生入口新增兼容层。

## 4. 后续 RustDesk 方案（不进入当前执行队列）

当前只交付已知端点可达的 UDP+FEC 直连。公网打洞、连接竞争、中继和跨 NAT 恢复留给后续 RustDesk 方案，本轮不继续建设或验收现有原生 Relay/P2P。
“RustDesk 方案”尚未确定为直接集成其代码、对接其服务器或参考其机制，当前不新增依赖或许诺协议兼容。保留会话与媒体/平台边界，
后续据此接入已选定方案，不为远期方案预建传输插件层。直连必需的背压、FEC、发送节奏、超时和局域网恢复仍属于当前范围。

## 5. 验收与交接

- 当前处于目录迁移检查点；现有代码和 APK 仍包含 RTC/Relay/WS 媒体回退，不得将其标记为符合新产品边界的候选包。
- 取消原生 RTC、Relay、P2P、WS 视频回退待测项；验收 UDP+FEC 视频、音频恢复、控制可靠性、文件并发隔离、语音、剪贴板和录制。
- Android 当前无 USB 手机；接入后只覆盖安装，不卸载、不清空数据，每次真机测试不超过 5 分钟。
- Windows 使用 `build_cpp_*.bat` 聚焦构建；修改的运行产物同步到 `build_official/dist` 并逐一核对 SHA-256。
- SDK 验证覆盖销毁后排队回调、分发时注销、回调内关闭与重复启动/停止；Web 侧必须验证保留的 RTC 路径未被误删。
- 设置与入口回归确认无强制通道、协议优先级或自动选择开关，旧设置值不能恢复已退役路径。
- 性能/设备/API/无障碍实机矩阵仍按此前决定跳过；签名、FFmpeg 发布输入和真实应用授权等现有交接条件保持适用。
