# PostgreSQL 应用部署与预约边界

2026-09-17，实施中，以下条款尚需 repository 与真实节点验收；不能作为已交付能力。

## 部署不是机器在线状态

每条部署明确 application、node、安装根目录、资源绑定、最大实例数、管理员配置 revision 和指定的应用 revision。
同一 application/node 只有一条稳定部署身份；修改配置不另造相同工作区。Game Hook 的安装根目录必须是显式 Windows 绝对目录；
WebView/RDP 不借用 Game Hook 路径字段。路径校验不是执行授权，启动仍须满足私有 Job 与完整路径 AND 条件。

Ready 回执必须同时匹配部署配置、应用版本、节点连接代际、控制 epoch、端点版本。新连接、配置修改或应用版本改变后，
旧准备结果只能作为历史观测，不能准入。节点只上报自己的部署，不能修改配置、owner 或业务授权。
准备失败原因用有限代码，不存任意脚本输出或包含凭据的原始错误。

DB 阶段先实现明确容量与事务预约；P3 才交付多 GPU 遥测硬过滤/评分和真实绑定验收。
未指定 GPU 不表示任意 GPU 都能提供独立容量；只能使用经过节点验证的整机预算，不能虚报多卡隔离能力。

## 实例和端口

- 实例指定 user 或 guest owner，严格二选一；Android 仍是 CloudApplication 目标，不使用设备/账户替代。
- 创建事务重新检查主体、ACL、应用/部署版本、节点新鲜度与对账、排空/禁用、部署容量和整机容量。
- 端口只能从节点本次报告的应用区间预约；同一节点活跃端口唯一。不同部署也不能抢占同一端口。
- request_id 按主体隔离并绑定请求摘要。重试返回同一个已提交结果；相同 ID 不同正文拒绝。
- 预约、实例与待发命令在一个事务提交；提交之后才发网络命令。不在数据库事务中等待节点执行。
- 失联/超时/进程重启转待对账，占用仍保留。不能凭超时或用户数为零释放端口或重复启动。
- 确认停止/未运行才能释放预约；晚到 Start/Ready 不能改变新的 Stop 或控制代际。
- RDP 工作区身份是 application/node；不同访问主体不另建 Windows 账号。运行实例结束不注销 Windows Session。

管理员禁用/修改部署不自动驱逐已占用资源；减少容量可能让可用数为零，但不能删除现有占用来迎合配置。
任何物理清理必须由节点按已授权实例身份和既定模式规则执行；数据库软删除不是任意进程/路径清理指令。

## 验收映射

DB2-B：管理角色、节点越权、模式路径、CAS、准备回执版本/代际、禁用与重启。
DB2-C：两个独立进程争最后名额/端口、相同请求重试、不同主体隔离、提交前故障和提交后响应丢失、重复投递和晚到回执。
DB2-D：RDP 工作区稳定身份、busy、凭据绑定和恢复后的未知占用。
数据库层通过后仍须接 Service/Console/客户端真实链路；不得用合成节点回执代替真实执行验收。

## 命令下发的实现约束

预约的 owner 与原始准入凭据分别记录：user 关联 login_session 和当时 authorization_revision；guest 关联 guest session 及 revision。
下发 Start 前重查原始会话到期/撤销、当前授权版本、ACL、准备版本、控制代际与维护状态。
只保存 user ID 无法判断“预约后、下发前退出登录”，不能满足撤销边界。用户通过新的合法会话查询自己历史实例，不会让旧命令自动恢复授权。

命令 claim 与实例状态变化同事务；发往节点的 command ID 在重投时不变，lease ID 每次改变，实例 revision 只能递增。
Stop 递增实例 revision，取消旧 Start，节点也必须按实例 revision 拒绝晚到 Start；只有 PG 行锁不能隔离已提交的网络副作用。
重复相同完成回执应幂等，不同结果的重复回执拒绝。过期 lease 的回执不能覆盖新状态。

从未 claim/下发的预约可以在明确取消后释放；曾经 claim 的 Start 即使超时也可能已经执行，必须保留占用并对账。
节点明确证明本实例未运行、或精确停止完成之后才释放。RDP 的“停止完成”只结束本次运行时/传输，不包含 Windows Session 注销。
Console 重启、节点重连、凭据轮换后先废止旧命令，逐个核对稳定 instance/launch 身份；未知实例阻止 Ready，不按 PID/端口收编或清扫。
