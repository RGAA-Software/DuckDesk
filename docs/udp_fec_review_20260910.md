# Native UDP/FEC 审查与第一轮修复（2026-09-10）

> 后续实施入口：[Sunshine / Moonlight 对齐实施方案](native_udp_fec_upstream_implementation_plan.md)。按最新范围裁决只改 UDP 音视频；本文提到的 WS/实例/连接恢复后续工作不纳入本期。

## 结论

目前的问题不只是冗余比例低。收包判丢、参考链恢复和反馈统计存在正确性缺口；不能声称当前控制策略已经达到 Sunshine/Moonlight 的水平。

参考源码（只读，未修改）：

- `D:/source/Sunshine/src/stream.cpp`：按 RS 255 分片限制计算单块容量，大帧拆多个 FEC 块；超过其协议块数上限才关闭 FEC。使用配置的冗余比例和协商的最小校验包数，并有发送节奏控制。
- `D:/source/moonlight-qt/moonlight-common-c/moonlight-common-c/src/RtpVideoQueue.c`：统计数据/校验包、缺包位置及块信息；按足够的不同分片恢复。该版本也会在下一帧到来时放弃未完成帧，不能说它提供任意跨帧乱序窗口。
- 同目录 `VideoDepacketizer.c`：区分等待 IDR 与参考帧失效恢复；恢复需要视频帧语义，不是收到请求就宣布恢复。

## 本轮已改代码

1. 删除 EOF 提前判丢：帧尾先到不证明其他 UDP 包已丢失。仍在下一帧到达时尝试恢复后判丢。
2. 禁止未经编码器确认的 RFI 标记解除客户端参考链阻塞。Render 不再把收到请求后的下一张发送帧标成恢复帧。
3. 客户端丢帧改为请求 IDR，所有屏幕共享 1 秒节流；无可解码画面时继续固定周期补请求，不使用指数退避。这是保守正确性方案，不是完成版低开销 RFI。
4. 首次接入必须等待关键帧。迟到的旧关键帧不能重置帧序号水位；连接重建通过显式 `Reset()` 清理状态。
5. 单块数据分片小于 255、但目标冗余使总数超过 255 时，保留能容纳的校验分片，不再突然归零。数据分片本身达到 255 时仍没有保护，必须后续实现多块 FEC。

涉及公共 UDP 协议实现、Native SDK 接收端及 Render UDP 发送端。未修改第三方 RS 实现或 RTC。

## 尚需做的性能工作（没有宣称完成）

1. 大帧多块 FEC：明确块序号/块总数、块内分片编号及帧级元信息；Windows/Android 同步更新。测试关键帧、多块乱序、丢整块和超界包。
2. 重做反馈口径：当前 `HandleFrameStatus` 把所有状态算成完成帧、所有缺片算成恢复片，而丢帧统计依赖关键帧请求次数。节流后请求数不等于丢帧数，因此当前 5 秒调节不能当作准确丢包控制。
3. 发送预算：当前固定 80 Mbps 节奏与异步发送排队，不能代表实际链路带宽或有效出包节奏。需记录队列时间/长度，限制过期视频积压，并将编码码率与冗余开销共同纳入预算，不能拥塞时只加 FEC。
4. 有界跨帧乱序等待与尾帧截止时间；超时依然请求恢复，不无限堆积或把参考链断裂的 P 帧送入解码。
5. 编码器级 RFI 完成信息：必须绑定实际编码帧及屏幕，处理在途帧和失效区间，支持失败时回退 IDR；未完成前维持本轮安全路径。

## 会话与测试边界

当前 Render 的 UDP 心跳超时已只移除媒体端点，不发逻辑客户端断开、不释放控制租约。此前心脏应用日志中随后确有 WS 断开，之后触发 5 秒无人连接回收，不能归因于 UDP 单独触发回收。

仍需独立完成：WS 在线时 UDP 断流自动重探测（SDK 当前 unavailable 状态锁存）、WS 短断线应用保留策略、Console 确认实例结束后停止针对旧端口的无效连接。不要把延长 UDP 超时当作这些问题的修复。
