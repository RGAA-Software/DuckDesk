# 双端 UDP 定位、恢复重试实验与本机网卡断开（2026-10-11）

## 本批结论

direct 混传确有成批 UDP 包在两端网卡捕获点之间缺失，已超出仅凭视频日志推测的阶段。首次修复提交附近的一个发送窗口中，18 个 UDP 包全部未出现在对端捕获；但加密包头不能逐包证明它们属于哪一帧。降低参考恢复重试时间的候选未证明整体性能改善，已完整撤回。随后强制 Relay 对照发生本机 Realtek 硬件无响应重置，自动重连窗口先于网卡恢复耗尽；该轮不是 UDP 短抖动性能证据。

## 双端捕获

本机与 90 均先确认 Pktmon 未运行、过滤器为空，添加唯一临时 UDP/4613 筛选器，160 字节截断，multi-file 捕获所有组件。从握手前覆盖到测试退出后，两个分片中第一个非空、第二个为空；两端停止均报告无 ETW 事件丢失。随后导出本机 TCPIP 75 / NIC 13，90 TCPIP 51 / NIC 10。远端文件只在 `D:\112233\iroh-paired-udp-20261011`。两端捕获已停止，过滤器已移除。

按 UDP 加密负载前 64 字节 SHA 匹配，筛选实际公网对端，排除发现候选，不直接相减两台机器墙钟。各层无重复指纹，所有接收包均能匹配发送记录。

| 方向 | 发出 | 收到并匹配 | 发出但对端未捕获 |
| --- | --- | --- | --- |
| 90 → 本机 | 91546 | 89800 | 1746，约 1.91% |
| 本机 → 90 | 64531 | 62788 | 1743，约 2.70% |

两主机 NIC 和 TCPIP 层指纹集合分别完全相等：没有发现已经到达网卡捕获点却未上交 TCPIP 的包。不能由此定位具体路由器、线缆、驱动或 NIC 硬件故障；NIC 捕获点也不是物理线路分析仪。接收包相对最小匹配时差的增长：前向 p95 23.15 ms / p99 48.93 ms / 最大 87.40 ms，反向最大 79.42 ms。这是相对延迟增长，不是绝对单向延迟。

第一轮 64 MiB 不可压缩文件往返 24.137 秒，SHA 相等；实际 direct `39.71.45.66:4613`，55.1–59.3 FPS，3 次 >100 ms、最大 169.9 ms。全部 3 次关联参考恢复，但其中一例还包含恢复开始前的约 103 ms 完整接收间隔，不能把整段都称为恢复定时器等待。

Client 的 frame=297 等待 137.452 ms，7 个完整帧因缺失参考未交付。对应 Render 首次修复 frame=290 在请求后 4.944 ms 提交；同一服务端时钟的提交前 1 ms 至后 16 ms 窗口发出 18 包（16 个 1129 字节、61/49 字节各一），全部在对端缺失。第二次请求后 frame=297 才恢复。另一次 frame=1221 等待 129.054 ms，首次修复 frame=1215 提交后的短窗口没有线上包，仍可能含发送排队；不能将全部修复失败都概括成同一物理丢包位置。

捕获身份及逐事件分析：`20261011_paired_udp_capture_identity.json`、`analysis.json`、`nic.json`（后两者同样带 `20261011_paired_udp_` 前缀）。原始捕获保留 `.cache/iroh-paired-udp-20261011/`，远端原始 ETL 不删除。

## RTT 重试候选：验证后撤回

参考只读 Moonlight common-c `e95feaf4951b8dc774671a5d6a1c31d76d78e3ac` 的 `VideoDepacketizer.c`：完整帧继续推进失效参考范围，控制线程合并请求。试改只对 iroh 参考恢复依据 RTT 选择 `min(100 ms, 33.334 ms + 2*RTT)`，仍要求完整帧进展；保留 500 ms IDR 升级、无进展时 4 秒保护，不动文件额度、QUIC、编码器和 90 安装。

| 候选 direct 复测 | 见 repeat JSON | 53.4–57.3 | 6 / 195.2 ms |

## 用户报告的断开

强制 Relay 实际媒体选中 90（双候选仍可用；脚本 `--pin-90` 本身不是已固定路径的证明）。该轮在中途发生全连接不可达，最终 89.685 秒时文件测试以 `FILE_TRANSFER_TIMEOUT` 退出，不能记录为往返通过。

本机日志时间线：

- 00:13:00.551：`iroh.connect outcome=network_lost action=readmit`。同时 BJ Relay 报 Ping timeout，90 Relay 随后报 Send timeout；两者重连均超时。
- 00:13:02–08：Console endpoint refresh 四次 `unavailable http=0`。
- 00:13:09.083：`IROH_RECONNECT_EXPIRED`。`iroh_dialer.cpp` 当前重连预算为固定 8 秒。
- 00:13:13.608：Windows NDIS 10400，Realtek Gaming GbE 硬件停止响应驱动命令，开始重置，本次初始化以来第 17 次。驱动仍为 10.43.723.2020 / 2020-07-23。
- 约 00:13:23.666：iroh home Relay 更新到 90，后续日志出现已连接状态，说明承载恢复晚于业务重连预算。
- 00:14:14.834：测试器等待文件完成超时后退出，不是这一刻才开始掉网。

系统重置事件晚于应用最初断开，不能当成精确硬件故障开始时刻。两 Relay、Console 同时不可达，加上本机 NDIS 明确报告，支持本机网卡故障是这次长中断的重要原因。90 无同时间 NDIS 重置，三服务 Running；Render 在其本地 00:13:06.175 进入最后客户端离开后的 10 秒宽限期（两机时钟有约 5.68 秒偏移，不直接比较墙钟）。当前 8 秒重连预算无法覆盖这次恢复；单独增大客户端预算也不能忽略服务端实例已退出的事实。

本轮短 UDP 丢包捕获发生在 00:03–04，系统重置发生在 00:13。两者必须分开记录，尚不能证明前者全部由同一网卡故障造成。断开证据 `20261011_disconnect_{client,routing,render}.log`、`20261011_disconnect_ndis.json`。

## 精确下一步

先把本机网卡硬件无响应作为单独环境故障调查，结合可用的另一网卡/机器对照和错误计数确定短丢包是否也来自该端；不得直接把系统事件当作可以靠调 UDP 定时器修复的问题。同时梳理客户端重连预算与 Console 配置的实例宽限期，避免网络尚未恢复就永久耗尽，也不擅自复活已停止的应用。媒体主线继续根据双端包证据定位突发发送/排队，针对性处理文件与视频共享承载。不要重做已否定的 RTT 重试与自适应额度实验；性能、NAT/长期稳定性、Windows/Linux 收束、Android 最后仍未完成。
