## 实际缺口与修改

Linux 完整包原来有镜像、Compose 和 SHA 清单，但加载、核对和启动依赖手工操作。
Compose 默认用目录推导项目名；新包放到不同目录后直接启动可能创建第二套服务并产生端口冲突。
配置原来相对当前包目录，新目录升级也容易丢失已有配置位置。

- `deploy/relay/deploy.py` 随完整镜像包交付，并纳入清单。支持离线核对及部署；明确指定既有 Compose 项目名、外部配置目录。
- 替换服务前检查完整包 SHA、Compose 解析、加载镜像 ID/平台及镜像内运行文件 SHA。检查失败时不调用 `compose up`。
- 升级仅更新该项目的 Relay 服务，不执行 `compose down`、不改外部配置。配置目录只读挂载，不自动创建空目录。
- 启动后核对容器状态、镜像和实际运行文件；Console readiness 明确为 `not_checked`，不以进程存活代替可用连接。
- 自定义主机 TCP/UDP 端口由参数传入，容器内固定 4605，与现有镜像一致。
- Windows 继续使用完整 Server Setup，已有共享 TLS ACL 和安装证据直接复用。更新过时的 M1/M2 文档状态，没有改 Windows 安装实现。

## 验证

`python -m unittest scripts.tests.test_relay_linux_package -v` 在本机 Windows 和 WSL Ubuntu 20.04 / Python 3.8.10 各通过八项：

1. 损坏镜像包在任何 Docker 调用前被拒绝。
2. 缺少清单文件被拒绝。
3. 缺少外部配置时不操作现有容器。
4. 加载镜像身份错误时不替换现有服务。
5. 更换包目录仍沿用相同项目、配置和自定义端口，配置字节保持不变。
6. 镜像内运行文件 SHA 不符时不替换现有服务。
7. Compose 解析失败时不加载镜像。
8. 启动后容器已退出不能报告成功。

上述 Docker 生命周期由模拟结果覆盖，不当作真实安装证据。
另用真实 Docker Compose 5.5.1 执行 `config --format json`，检查项目名、带空格的外部配置路径、只读挂载、禁止创建空目录、
5605/TCP 和 5606/UDP 映射到容器 4605。该检查没有启动容器。打包入口 `bash -n` 和活动差异 `git diff --check` 通过。

前序基线提交前另核对隔离 iroh 1.3.0 全部 84 文件及最小补丁 SHA；不重复既有媒体、容量、故障与业务功能测试。
