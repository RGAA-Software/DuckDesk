# Complete-frame receive feedback and recovery — 2026-10-09

This increment addresses recovery amplification and encoder feedback. It does not claim that the Relay TCP queue can discard already-enqueued old frames, or that P0–P7 is complete.

- `VideoStreamReceiver` reports fully assembled frame identity/size before reference-chain admission. Partial loss does not request RFI. Undecodable complete frames still prove network progress.
- `VideoRecoveryPolicy` waits for complete progress before rapid retries; an incomplete/static source retains a sparse four-second recovery watchdog. Late duplicate/parity shards do not arm this watchdog. Healthy static streams remain idle.
- Iroh send failures only report backpressure. Decoder `kInsertKeyFrame` and assembly recovery enter the same server-side recovery gate, including all-monitor requests. Existing reference invalidation remains preferred when usable.
- New existing-session control message `MediaReceiveFeedback` reports per-stream cumulative complete-frame/encoded-byte counters and receiver-local elapsed time every 250 ms, including no-progress reports. At most one feedback write per stream is pending; cumulative counters tolerate skipped reports. No token, ticket or second authentication was added.
- Server tracks up to 256 offered frame identities per stream and measures acknowledged progress using its own steady clock. Missing/stalled feedback while frames remain outstanding reduces encoder rate even when local sends succeed and RTT has not risen. Complete reception of the latest offered frame leaves a static stream uncongested. Stale/nonmonotonic counters are ignored; receiver measurements cap bitrate during congestion, not during normal low-complexity scenes.
- QUIC still controls packet congestion and pacing. End-to-end queue age, rendered-frame/decoder backlog feedback, and adaptive FPS remain separate pending work.
