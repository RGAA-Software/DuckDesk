# Direct 游戏/文件混传的帧交付停顿定位（2026-10-10）

本批补充接收端参考恢复诊断，执行纯视频 → 64 MiB 文件往返混传 → 纯视频对照。三轮实际路径均为 direct `39.71.45.66:4613`，不是 Relay。确认发送准入背压和参考恢复等待两类机制，尚未确认所有异常的物理丢包或具体队列位置；性能问题未关闭。

## 指标口径

`IrohConnection::ObserveVideo` 统计交付解码器的帧，不是所有完整组装的帧。缺失参考时，完整但不可解码的后续帧也会被丢弃/扣留交付，不是缓存后再集中解码。新增 `iroh.reference_wait` 记录等待时长、期间完整但未交付的帧数；`iroh.frame_transit` 增加 `reference_ready`。

`assembly_call_us` 是该次组帧函数调用的执行耗时，不包含等待分片的总时间。`source_gap_us` 是发送端封包提交间隔，包含传输准入背压，不能直接解释为游戏渲染慢。恢复请求的 `local_send_us` 是本地可靠 QUIC 写入完成耗时，不是远端接收或线上时延。两机墙钟有偏移，按帧号关联事件，仅在同一主机内计算间隔。

### 参考恢复实例

- Client 23:33:05.910 完整收到 frame=259，但 invalid_reference=258，开始等待参考恢复。首次 RFI 本地写入 69 微秒；23:33:06.019 再次请求，本地写入 58 微秒。
- Client 23:33:06.083 收到可交付修复帧 269，等待 172891 微秒，期间 9 个完整帧未交付；解码器帧交付间隔 184.3 ms。
- Render 首次收到该参考恢复请求后 9209 微秒提交修复帧 262；该帧没有在 Client 形成可交付帧。约 100 ms 的重试后，第二次请求对应修复帧 269（服务端请求后 14528 微秒提交），客户端恢复。
- 这证明主要时间花在等待可用参考恢复，而不是本地恢复请求写入。没有本轮双端 UDP 包头证据，不能确定首个修复帧在网络、端点队列或不完整组装的哪个位置失效。
- 本轮共 19 次 RFI，无 IDR；本地请求写入最大 2298 微秒。另两次长参考等待为 165811 / 180679 微秒；后者同时存在源提交停顿，不能全归为参考恢复。

### 发送准入背压实例

frame=1275 的交付间隔 224.0 ms，源提交间隔 236066 微秒，当次组帧调用 22 微秒。Render 此前记录 `capture_credit` 阻塞 216969 微秒，恢复后约 7 ms 提交。视频飞行额度缩到约 32 KiB，文件额度仍为固定 256 KiB。捕获输入约 60 FPS，稳定阶段编码任务约 6–7 ms，不能将这次停顿归于 GPU 编码慢。

其余 9 次事件的源间隔约 16–67 ms、完整接收间隔约 105–155 ms、组帧函数调用 9–34 微秒，定位范围是提交后至完整接收，尚未区分网络与端点队列。
