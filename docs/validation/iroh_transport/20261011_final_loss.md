# 不可恢复帧的立即修复

## 证据与修改

回放 `20261011_media_logging_direct_2` 最初90秒的5,218帧无载荷分片记录：29个观察到的不完整块，没有任何一个在下一帧到达后又收到足够补齐的分片。此结论只覆盖记录窗口，不证明未观察到的包丢在何处。没有据此扩大接收缓冲。

其中encoder587/wire411需要13片，只观察到12片；encoder599/wire422需要19片，只观察到17片。源端全部分片本地提交成功并不等于网络交付成功。

客户端已在mono1115146217982确认wire412不可恢复，但等到1115146233077才向上层提供invalid_reference587，额外等待15,095µs。另一例wire422在1115146354768确认丢失，1115146370320才提供invalid_reference599，额外15,552µs。这只是本地可消除的部分，不能把整段91–242ms恢复空档归于这15ms。

只读核对Moonlight media core `e95feaf4951b8dc774671a5d6a1c31d76d78e3ac`，`src/VideoDepacketizer.c::notifyFrameLost`在不可恢复时请求RFI，避免等待下一完整帧。本项目此前仅把队列loss当作telemetry，直到下一完整依赖帧才请求修复。

新增与预测telemetry分离的`VideoQueueOutput::final_frame_loss`，在真正退休缺失帧/块时设置；不改变已有Moonlight oracle的分片排序/FEC/loss序列。已有参考时立即提供最早无效编码参考，预测丢片不触发；同一Feed完成IDR/RFI后清除请求。编码计数最大值请求IDR，避免+1溢出。

第二处遗漏：队列此前发过speculative loss，退休该帧时按Moonlight约定不重复发loss事件；由于项目未消费预测请求，仅依赖loss vector会漏掉最终丢失。独立final flag覆盖该情况。

## 验证与限制

先保存实际19+4分片、仅17片到达的旧实现失败；再保存“预测通知压住最终通知”的失败。第一次FEC回归误用了默认minimum_parity=2，却断言只有1校验片；失败日志保留，改为显式1片并使用单调到达时间。

回归覆盖立即请求/合并、预测丢帧后FEC救回、预测后真正退休、缺整帧、同Feed新IDR消除请求、编码计数溢出及既有参考语义。此补丁尚不证明公网反复卡帧已消除，S3仍未完成。
