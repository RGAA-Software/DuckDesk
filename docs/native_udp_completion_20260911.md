# Native UDP 实现收尾与集中验收（2026-09-11）

范围：完成 Windows Native 媒体发送预算、参考恢复与背压；WS 控制、鉴权、文件及 Web RTC 不改变。
Android 按用户要求延期；不调整本机网卡、路由器或端口映射。

## 实现

1. 预算复用应用现有的码率配置。Native 连接后将它作为**音视频总预算**，不再直接全部分配给视频编码器。
   未连接 Native 时不改变原编码码率；RTC 的独立配置路径不变。
2. 预算参考 Sunshine `3cba9baebac882b336be3ebe129ee612cb189853` 的 `rtsp.cpp`，保留 FEC 与协议开销预留意图。
   明确适配差异：Pixels 音频采用 20 ms、固定长度保护分片，必须按线上包长预留，不能套用 Opus 码率估算。
   1400 字节配置：每秒 50 个数据包（1388 字节）与 25 个校验包（1400 字节），再保守加入 IPv6/UDP 的 48 字节，
   音频预留为 **864000 bit/s**。视频发送预算为总预算减去音频预留；有效视频编码预算再按 FEC 预留及协议余量计算。
   8 Mbps、20% FEC 时：视频编码 **5208800 bit/s**，视频线上发送预算 **7136000 bit/s**。
   因而新旧都显示“8 Mbps”并不代表编码质量相同；不能把降视频编码码率带来的改善全归于 FEC 算法。
3. 发送使用跨帧时间锚点、至多 1 ms 字节量/64 KiB 的批次；计入视频封装、校验与 IP/UDP 头，不再固定 16 Mbps。
   音频和视频各最多一个待执行批次，实际 socket 非阻塞逐包发送；超时取消尚未执行的数据，停止期间取消等待。
   保留跨批次时间相位，迟到补偿最多 1 ms；不能每次按实际唤醒重置，否则亚毫秒定时误差会不断降低吞吐。
   这是明确记录的公网发送适配差异，不允许长时间调度停顿积攒无限补发额度。
4. Native 编码后待发送队列限制为 4 帧、4 MiB，另有最多一帧正在发送；排队超过 100 ms 的帧不继续积压。
   本地丢帧发生在 transport 序号分配前，因此必须请求新 IDR，并阻止依赖链继续发送。
   队列中的旧 IDR 不能确认后来发生的丢帧；按流代次区分。Web RTC 保留原派发路径。
5. NVENC 在下一次编码前合并 RFI 起点；按实际编码输出 timestamp 列表选择参考帧，不再逐个遍历采集帧编号。
   无有效旧参考、窗口不足或调用失败时回退 IDR。请求入队不等于恢复确认，只有编码器实际输出才设置恢复标记。
   编码器集合的替换、恢复、编码和关闭串行化；补全 RemoveAll 的实际资源关闭。
6. 保留原代码于 `backup/native_media_completion_20260911/`；不增加旧协议回退或另一套产品媒体通道。

### 最终复验结果（09:17–09:20）

3 分钟真实 Windows Client，120.01 秒大范围鼠标运动，7491 次移动。35 个统计窗口：平均 **29.9486 FPS**，最低 **27.8 FPS**，
最大完整帧间隔 **132.6 ms**，超过 100 ms 共 **2 次**。`receive_window_pass=false`，不放宽门槛，不标记整体验收通过。

90 侧同一会话：**0 次队列丢帧、0 次未完整发送**；编码约 30 FPS。异常窗口附近 socket 发送错误/超时均为 0，批次等待最大 96 us。
客户端异常窗口同时出现视频丢帧、8 次 RFI 和 6 次音频 PLC；其余窗口接近 30 FPS，另有被 FEC 正常恢复的分片。
这些证据排除了本轮已修正的持续队列丢帧回归，但尚不能定位突发损失发生在路由器、两端网络栈、网卡还是接收调度。
不能以“90 做端口映射”直接判定路由器故障，也不能以 socket 发送成功证明对端已经收到。

已检查游戏运动过程的截图，未见明显坏参考块；未录制连续画面，不作整段无花屏的绝对承诺。
测试实例按正常接口停止，本机和 90 的 `px_service` 均恢复/保持 Running。两轮均为每轮 3 分钟，不继续反复调整参数刷通过结果。

结论：本轮预算、参考合并、背压、取消与时钟回归的开发/构建已交付；**Windows 稳定性验收仍有上述突发窗口待解决**。
下一项应在保持现有参数的情况下对异常窗口做两端同时间线收发定位；不默认修改网卡或路由器设置。

后续定位开发与实测记录见 [分片时间线诊断](native_udp_packet_timing_20260911.md)，以下历史结果不代表后续版本的验收结论。

## 已知边界

- 这是适配既有 Pixels 控制与音频帧长的媒体实现，不是完整 GameStream，也不能宣称所有端到端行为逐字节等同。
- 队列 100 ms 是本地资源/延迟保护策略，不是已测得的上游性能基线，也不是降低验收门槛。
- 配置不是链路测速结果；若总预算超过真实路径能力，固定冗余不能恢复整块/整帧完全丢失。
- 多显示器并发的总编码预算分配、Android、上游同配置性能基线及完整音画同步测量不能用单游戏 Windows 验收替代。
