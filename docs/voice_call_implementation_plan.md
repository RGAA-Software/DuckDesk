# 远控语音通话工程实施计划

> 文档状态：执行基线，2026-08-23。
>
> 关联设计：[voice_call_design.md](voice_call_design.md)
>
> 测试与发布门禁：[voice_call_test_acceptance_plan.md](voice_call_test_acceptance_plan.md)

## 1. 目的与最终交付

本计划把语音通话从当前 Windows 原生 MVP 推进到可发布能力。最终交付必须满足：

1. Windows 原生客户端和 WebClient 均能从远控悬浮控制条发起、接受、拒绝、静音和挂断一对一语音通话。
2. 被控端必须在当前交互用户会话中显示可信、可操作的来电界面；远控权限不能替代麦克风授权。
3. 桌面系统声音、通话麦克风和对端语音是三条独立音频流，任一流启停不得破坏另外两条。
4. Windows 扬声器外放场景启用 AEC、NS、AGC；设备切换、热插拔、睡眠和网络变化后可以恢复。
5. 语音信令和媒体与已认证的 `device_id`、`stream_id`、`call_id` 严格绑定，旧响应、伪造帧和挂断后媒体不能恢复麦克风。
6. 支持产品启用/禁用、审计、安装升级、旧版本兼容和异常恢复，不保存语音内容或可复用凭据。
7. 所有 P0 自动化和人工验收项通过，P1 发布矩阵达到本计划约定后才允许声明“语音功能完成”。

不在当前版本范围：群聊、录音、语音留言、SIP/PSTN、自动接听、移动端后台通话。Android 作为后续独立里程碑，不阻塞 Windows/Web 首次正式发布。

### 2.1 里程碑状态口径

状态只能使用以下五种，避免把“写了代码”和“完成验收”混为一谈：

| 状态 | 含义 |
| --- | --- |
| 未开始 | 尚无可评审实现 |
| 开发中 | 已有代码，但实现、测试或文档仍不完整 |
| 已实现 | 代码和单元测试完成，尚未通过目标环境验收 |
| 已验证 | 指定环境与范围已经通过，未覆盖项明确列出 |
| 发布验收 | 候选安装包通过全部发布门禁，可对外交付 |

截至 2026-08-23：M0 为“已验证”；M1 为“已实现/核心 Console 路径已验证”，尚缺锁屏、RDP、切换用户等会话矩阵；M2 为“开发中/核心音频链、设备选择、真实WASAPI和2小时闭环已验证”，尚缺双物理机音质和热插拔/蓝牙；M3 为“开发中”，已实现可靠链路有界语音队列、拥塞丢旧和 RTC 精确 stream 路由，尚缺传输/弱网/并发矩阵；M4 为“已实现/Chrome核心路径已验证”，90号机已通过正式Panel接受/拒绝/超时、双向RTP、独立静音和清理，尚缺生产HTTPS、Edge、真实浏览器麦克风异常与虚拟屏并发矩阵；M5 为“开发中”，日志关联 ID 已脱敏，策略动态撤销、审计和完整安装矩阵未完成；M6 未开始。实测记录见 [M1报告](voice_call_m1_test_report_20260823.md) 与 [M2报告](voice_call_m2_test_report_20260823.md)。任何后续状态变更都应同时更新测试结果链接，不能只修改文字状态。

## 3. 统一完成定义（Definition of Done）

每个工作项只有同时满足以下条件才可标记完成：

- 代码：Release/RelWithDebInfo 编译通过，无新增高等级编译告警；协议生成物与源定义一致。
- 行为：正常、拒绝、超时、取消、断线、重启和重复消息路径均有确定结果，清理幂等。
- 测试：新增逻辑有单元或组件测试；跨进程能力有集成测试；用户路径有真实 UI E2E。
- 兼容：功能关闭和旧客户端行为可预测，不发送对端未声明支持的消息。
- 安全：权限校验在资源创建前完成；日志不包含 PCM、Opus payload、密码、token 或完整 SDP。
- 观测：关键状态转换、结束原因、队列、丢包、PLC、underrun 和设备重建可诊断。
- 文档：设计、配置、用户提示、测试结果和已知限制同步更新。
- 证据：按测试计划保存机器可读结果、版本、哈希、日志摘要和必要截图；人工项有执行者与时间。
- 回归：虚拟显示器、切屏、桌面声音、键鼠、文件传输和安装升级的 P0 回归通过。

## 4. 工作分解与交付顺序

### M0：冻结并收口当前原生 MVP

目标：建立可以稳定复现、测试和回退的语音基线。

| ID | 工作项 | 依赖 | 交付物 | 完成标准 |
| --- | --- | --- | --- | --- |
| VC-M0-01 | 核对 proto 编号、字段与 Web 镜像 | 无 | 冻结的 v1 协议说明 | 消息编号不冲突，生成物一致，旧端忽略未知能力 |
| VC-M0-02 | 整理 `px_voice_call` 状态机和音频端点边界 | 01 | 公共接口说明 | UI、网络、声卡职责分离，无跨层直接改状态 |
| VC-M0-03 | 补齐当前状态机/协议测试 | 01–02 | 自动化测试 | P0 边界、重放、超时、序号回绕全部覆盖 |
| VC-M0-04 | 固化90号机当前原生冒烟流程 | 03 | E2E脚本/操作说明 | 连接、首帧、呼叫、取消、挂断可重复执行且不依赖测试后门 |
| VC-M0-05 | 建立干净提交基线 | 01–04 | 独立可审查提交 | 变更边界清晰，版本变更与功能变更可追踪 |

退出门禁：`test_voice_call`、`test_client_voice_call_protocol`、`test_client_virtual_display` 全部通过；最终产物不含自动接受或绕过授权代码。

### M1：正式被控端来电与授权闭环

目标：由 `px_panel` 在正确交互会话展示产品级来电界面，替代 WTS/MessageBox 临时实现。

建议消息链：

```text
远端 VoiceCallRequest
  -> Render 校验认证 stream 和占用状态
  -> Render/Service IPC: IncomingVoiceCall(call_id, request_id, visitor, deadline)
  -> 活动会话 px_panel 展示非阻塞来电卡片
  -> Panel IPC: Accept / Reject / Timeout
  -> Render 二次核对 call/request/session/deadline
  -> 创建音频端点并发送 VoiceCallResponse
```

| ID | 工作项 | 依赖 | 完成标准 |
| --- | --- | --- | --- |
| VC-M1-01 | 定义 Render/Service/Panel IPC 消息 | M0 | 带 `call_id/request_id/stream_id/deadline`；响应可关联、防重放 |
| VC-M1-02 | 实现非阻塞来电 UI | 01 | 显示访问者、麦克风含义、倒计时、接受/拒绝；可键盘操作和读屏识别 |
| VC-M1-03 | 实现生命周期与幂等 | 01–02 | 远端取消、超时、断线、Panel/Render退出均关闭 UI 和资源；重复响应无副作用 |
| VC-M1-04 | 处理 Windows 会话变化 | 02–03 | 控制台、RDP、锁屏、解锁、切换用户的显示目标和默认拒绝策略明确 |
| VC-M1-05 | 移除生产 WTS/MessageBox 路径 | 01–04 | 正式构建只走 Panel UI；Panel不可用时 fail closed，返回可诊断原因 |
| VC-M1-06 | 自动化与人工 UI 验收 | 01–05 | 接受、拒绝、超时、远端取消、重复来电、并发来电均有证据 |

关键规则：Panel 只做展示与用户决策，最终授权校验和声卡资源创建仍在 Render；接受按钮不得直接绕过认证状态。锁屏或没有可确认的交互用户时默认拒绝，不自动接听。公开 `/panel` 继续服务 Web/原生客户端，内部 `/panel/renderer` 与 `/sys/info` 只允许本机回环连接。

### M2：Windows 音频质量与设备层

目标：形成可低延迟重建的 10 ms 音频处理链并完成外放回声控制。

| ID | 工作项 | 依赖 | 完成标准 |
| --- | --- | --- | --- |
| VC-M2-01 | 抽象 `IVoiceAudioBackend` | M0 | 采集、播放、枚举、默认通信设备、热插拔和错误回调可替换测试 |
| VC-M2-02 | 实现 Windows WASAPI 通信设备后端 | 01 | 48 kHz mono，event-driven，共享模式；回调无阻塞I/O和动态分配 |
| VC-M2-03 | 封装 WebRTC APM | 01–02 | 每通话独立 APM；10 ms `ProcessStream` / `ProcessReverseStream`，AEC/NS/AGC 可配置 |
| VC-M2-04 | 建立真实播放参考流 | 02–03 | 参考为实际送扬声器的 PCM；静音、音量和系统声音 ducking 后参考一致 |
| VC-M2-05 | 实现接收抖动缓冲与 PLC | M0 | 目标 60–100 ms、上限 200 ms；迟到/重复帧丢弃，断流不无限堆积 |
| VC-M2-06 | 设备选择和热重建 | 01–05 | USB、蓝牙、默认设备变化、睡眠恢复时暂停、清队列、重建后恢复 |
| VC-M2-07 | 音量、麦克风静音、扬声器静音 | 02–06 | UI状态与实际媒体一致；静音不停止状态机，不发送陈旧缓存帧 |
| VC-M2-08 | 音质和性能验收 | 03–07 | 满足测试计划的回声、延迟、CPU、内存、队列和2小时门禁 |

实现约束：APM 不创建 `PeerConnection`；Opus 和现有非 WebRTC 传输保持不变。若 WASAPI 后端未达到稳定门禁，可以保留 SDL2 为显式回退后端，但不得静默关闭 AEC 后仍宣称外放免回声。

### M3：会话、网络和多模块可靠性

当前实现：非 WebRTC 语音通过独立 worker 和最多5帧的有界队列发送；网络调用阻塞时丢弃旧语音并跳到最新帧，控制消息不进入该队列。RTC target-stream 回复已改为只投递精确 `stream_id`。这些行为已有确定性组件测试；直连/Relay/弱网和多负载实机数据仍是退出门禁。

| ID | 工作项 | 依赖 | 完成标准 |
| --- | --- | --- | --- |
| VC-M3-01 | 统一结束原因 | M1–M2 | `rejected/busy/timeout/no_mic/device_lost/disconnected/policy_revoked/takeover/error` 可追踪 |
| VC-M3-02 | 传输优先级与有界队列 | M2 | 控制 > 语音 > 视频delta；可靠链路只保留最新语音帧，不形成队头延迟 |
| VC-M3-03 | 直连/Relay/UDP/KCP一致性 | 02 | 信令语义相同，媒体不会进入文件传输队列，切换不重复建通话 |
| VC-M3-04 | 接管与多客户端竞争 | M1 | 同一目标只有一个活动通话；新会话按策略 busy 或终止旧通话 |
| VC-M3-05 | 进程与网络异常恢复 | M1–M2 | Service/Panel/Render/客户端退出、断网、休眠后资源必然释放 |
| VC-M3-06 | 负载与长稳 | 02–05 | 视频、系统声、文件传输并发下满足延迟和资源指标；2小时无持续增长 |

### M4：WebClient 双向语音

目标：WebClient 提供与原生客户端一致的产品语义，媒体优先使用 WebRTC 原生 audio track。

当前实现：WebClient 已按 capability、CMS `audio` 权限和浏览器安全上下文门控；只在用户点击并确认每次通话安全提示后请求浏览器麦克风，Panel 接受前不把 track 附加到 sender；响应严格匹配 `call_id/request_id`，超时、拒绝、挂断、刷新和设备 track 结束均清理媒体。系统声音和通话声音使用两条 audio m-line 与两个独立播放元素，麦克风/通话扬声器可分别静音。Render 仅在正式授权后转发浏览器 PCM，并复用同一个 WASAPI/APM 端点形成真实 AEC 反向参考。生产构建、19项状态/关联测试及90号机 Chrome 核心 E2E 已通过。当前服务器只提供 `http://IP`，浏览器会按安全上下文规则禁用 `getUserMedia`；正式发布需配置 HTTPS，测试专用 Chrome 安全源开关不得作为生产验收结果。

| --- | --- | --- | --- |
| VC-M4-01 | Web 状态模型和 capability 门控 | M0 | 未支持时按钮隐藏/置灰；页面刷新、重连不遗留假通话状态 |
| VC-M4-02 | 悬浮按钮和交互 | 01 | 呼叫、等待、已连接、静音、挂断、错误状态完整；支持键盘和可访问名称 |
| VC-M4-03 | 浏览器麦克风授权 | 01–02 | 仅用户操作触发 `getUserMedia`；拒绝、无设备、权限撤销有明确提示 |
| VC-M4-04 | WebRTC 上行 audio track | 03 | 请求 AEC/NS/AGC；轨道只在已授权通话期存在，挂断立即 stop |

### M6：正式发布验收

1. 冻结候选版本，记录 commit、版本、安装包及关键 DLL 的 SHA-256。
2. 在测试矩阵执行全部 P0；P1 按 Windows/GPU/浏览器/传输覆盖规则执行。
3. 90号机执行完整安装、原生、WebClient、虚拟显示器和卸载/恢复验证。
4. 双物理终端执行外放 AEC、双讲、设备热插拔和2小时通话。
5. 汇总失败、重试和修复提交；修复后至少重跑所属测试组及 P0 回归。
6. 无阻断缺陷、证据完整且人工授权路径真实通过后，才生成最终验收报告。

## 5. 模块边界与接口约束

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `px_voice_call` | 状态机、媒体序号、音频端点抽象、Opus/APM/队列 | UI、会话鉴权、具体网络路由 |
| `px_render voice_call` | 鉴权绑定、通话独占、资源生命周期、消息路由 | 伪造用户同意、管理页面展示 |
| `px_panel` | 来电展示、用户决策、策略入口、审计上报 | 直接启动采集、信任未经Render核对的请求 |
| `px_client` | 原生悬浮 UI、主控状态机、设备/静音控制 | 被控端授权决定 |
| WebClient | 浏览器 UI、权限、audio track 生命周期 | 在无用户手势时绕过浏览器权限 |
| 传输插件 | 按优先级交付控制和媒体 | 改写通话状态或缓存无限音频 |

所有跨线程/跨进程回调都必须携带关联身份，并在目标线程再次检查当前状态。音频 callback 只做有界复制或无锁入队；状态通知进入 UI 线程，禁止由网络线程直接操作控件。

## 6. 兼容与版本策略

- v1 capability：`voice_call_enabled=true` 且 `voice_call_protocol_version>=1` 才展示可用入口。
- 接收端必须容忍未知 protobuf 字段；发送端不能向未声明支持的对端发送 voice 消息。
- 音频格式不兼容时返回明确错误或拒绝 config，不能按错误采样率播放。
- 协议新增字段优先保持 optional/default 兼容；改变状态机语义时提升 protocol version。
- WebRTC 和 protobuf 媒体不能在同一通话重复发送；协商结果要固定到 `call_id` 生命周期。
- 版本降级后，已有配置不得导致 Render/Panel 启动失败；不识别字段按安全默认值处理。

## 7. 可观测性与诊断

每次通话至少产生以下脱敏字段：

- 协议版本、传输类型、端点类型、采样率、声道、帧长、Opus码率、APM开关。
- 状态转换时间和原因；关联 ID 仅记录短哈希或符合日志保留策略的值。
- `captured/encoded/sent/received/decoded/played` 计数。
- 丢包、重复、乱序、迟到、PLC、FEC、capture drop、playout drop、underrun。
- PCM队列、传输队列、jitter buffer 的当前值和峰值。
- 输入/输出设备重建次数、原因、耗时和最终结果。
- 通话期间 CPU、工作集、句柄、线程基线与峰值（测试构建或诊断模式）。

高频帧不得逐包写日志。正常模式记录开始/结束摘要和限频异常；诊断模式也不能记录音频 payload。

## 8. 风险、决策与降级

| 风险 | 影响 | 控制措施 | 允许的降级 |
| --- | --- | --- | --- |
| Session 0 无法可靠展示授权 | 用户无法接受或误授权 | Panel IPC、活动会话核对、fail closed | 拒绝并提示 Panel 不可用 |
| AEC参考与实际播放不一致 | 外放回声 | 在最终音量/静音后采集 reverse stream；自动化注入测试 | 明确耳机模式，不宣称外放可用 |
| 蓝牙 profile 切换 | 无声、格式变化 | 通信设备角色、设备通知、暂停/清队列/重建 | 回退默认通信设备并提示 |
| 可靠通道队头阻塞 | 延迟不断增长 | 独立有界队列、丢旧帧、延迟监控 | 暂停语音并报告网络差 |
| 多客户端争抢麦克风 | 隐私和资源冲突 | Render全局独占、busy响应、幂等清理 | 后到请求拒绝 |
| 浏览器权限/自动播放限制 | Web无声 | 用户手势触发、明确权限状态、播放解锁 | UI明确不支持，不能显示已连接 |
| 旧版本不识别协议 | 断连或假按钮 | capability门控和互通测试 | 隐藏入口，保持远控 |

## 9. 交付与评审清单

每个里程碑交付应包含：

- 设计或 ADR 变更，以及涉及模块和线程模型。
- 功能代码、生成代码和资源；第三方依赖的版本、许可证和构建方式。
- 新增/更新自动化测试及可直接运行的命令。
- 测试结果清单：通过、失败、跳过及原因，禁止只报“总体通过”。
- 对90号机或其他远端环境的变更、恢复状态和产物哈希；不保存密码。
- 已知问题、风险接受人、回滚步骤和下一里程碑入口条件。

提交建议按 M0/M1/M2/M3/M4/M5 拆分，协议与生成物、核心库、Render、Panel、原生客户端、WebClient、测试文档各自保持可审查。未经用户明确要求不自动提交或推送。
