## 1. 目标与范围

Windows Client 的普通远程桌面、GameHook、WebView 共用连接编排、媒体恢复和故障诊断。默认自动选择可用路径：
可达的局域网/公网直连优先，尝试 NAT UDP 打洞，必要时使用 Relay；连接中断后重新验证路径并恢复同一逻辑会话。
选路质量依据实际测量，不能仅凭“直连”标签长期选择明显更差的路径。

区分三个概念：

| 概念 | 含义 |
|---|---|
| 业务 | 普通桌面、GameHook、WebView、RDP 工作区、独立文件传输 |
| 路径 | 可达端点直连、NAT 打洞后的点对点连接、Relay 转发 |
| 载体 | 可靠控制/字节流、可丢弃的实时音视频数据报 |

P2P 是端点间建立通信的方式，不是新的编码器；Relay 改变经过的路径，不能修复错误的解码恢复逻辑。
统一的是授权、选路、状态、恢复和诊断，不要求 RDP 字节流与视频包采用相同的可靠性语义。

首批交付 Windows。协议定义必须表达端能力，Android 后续按能力接入，不冒充已经支持。
Web 客户端继续遵守 Direct Host WebRTC 约束；本提案不恢复中央 SDP/ICE、Coturn/TURN 或浏览器经 Relay 的 WebRTC。
网页端的跨 NAT 能力需要另行明确范围，不能用 Windows Native 的实现冒充网页能力。

这次需求允许设计 Native P2P 和自动回退；落地时需更新现有“UDP 失败无媒体回退”的运行策略。
跨 Relay 重建、RDP Relay 也属于新增能力，不把旧 P3 文档的验收结论套用于它们。保留 Relay 名称及现有非 WebRTC 数据协议。

## 3. 组件职责

| 组件 | 负责 | 不承担 |
|---|---|---|
| Console 内连接编排模块 | ACL、资源会话、节点/实例身份、连接计划、候选交换、Relay 选择和受权重绑定 | 音视频转发、解码、把一次选路算作一个新应用实例 |
| Service / Render | Service 复用管理长连接协调目标运行时；Render 决定实际接入、控制席位、监听端点并发送媒体 | 将客户端提交的任意地址当作可信目标 |
| Client SDK | 候选探测、控制与媒体选路、重连、拥塞反馈、向 UI 报告结构化状态 | 自行绕过 Console 更换资源或接管他人会话 |
| Relay | 保留可靠转发；新增受授权的 Native UDP 地址探测与转发能力 | 应用 ACL、许可证解析、RDP 解码、WebRTC signaling |
| Panel / Client UI | 进度、当前路径、降级/恢复原因和重试入口 | 自己另写一套 NAT/重连逻辑 |

连接编排先放在 Console 内，复用现有存储、事务与节点控制通道，不为本任务增加独立 Broker 服务。
Client 与 Render 共用协议值类型和恢复规则；平台 socket、网络变化通知与时钟留在适配器。

## 4. 分开选择控制和媒体路径

| 业务 | 可靠通道 | 实时媒体 | 无 UDP 时 |
|---|---|---|---|
| 普通远程桌面、GameHook、WebView | 直连可靠通道或 Relay 可靠通道 | 直连 UDP、打洞 UDP、Relay UDP | 经已授权可靠路径传输媒体，显示降级状态 |
| RDP 应用 | 直连可靠隧道或 Relay 可靠隧道 | 原生 RDP 字节流，不套用 Native 视频 FEC | 继续可靠隧道；不转成 Render 解码再编码 |
| 独立文件传输 | 直连或 Relay 可靠通道 | 无 | 继续可靠通道并受背压控制 |

例如：双方都在 NAT 后面时，可以先经 Relay 建立控制，再打洞让视频直接传输。
UI 必须准确显示“控制：Relay；视频：P2P”，不能把它标成“全部直连”。
只有视频打洞成功不等于控制、剪贴板、文件传输也能绕开 Relay。

RDP 首版支持直连可靠隧道和 Relay 可靠隧道；不承诺 TCP 打洞，也不把 Native UDP 视频打洞宣传为 RDP P2P。
若后续要求 RDP 与控制数据也完全经打洞路径传输，需要另一个可靠 UDP 载体验证切片，见第 9 节。

## 5. 建连流程

1. Panel 请求目标资源，Console 完成权限与实例调度，返回同一资源会话的连接计划。
2. 对 Console 管理设备，权限预检经现有节点管理长连接取得当前 Render 状态；不能因为 HTTP 直连失败而提前判设备离线。
   Render 在真正接入时再次原子检查控制席位和权限，避免预检与接入之间的竞争。普通 IP 直连仍允许不经 Console 使用现有授权流程。
3. Client 尝试可用直连控制路径；自动模式下延迟一个很短的竞速窗口启动 Relay 备用连接，不逐个等待长超时。
   初始建议窗口 250 ms，只是待实测的调优值。候选探测与逻辑会话接入分离；探测成功不能消耗两次接入凭据或占两个席位。
4. 原子选定并接入一个控制路径。已有 frontend grant、资源会话和 Relay admission 语义继续复用；不建立第二套客户端 ticket 产品。
5. Native 媒体并行验证已知端点与受授权 NAT 候选。先使用可用路径；Relay 可先出画面，P2P 随后验证成功再切换。
   初始打洞预算建议 2 秒，超时不继续阻塞首次连接；后台重试有退避和上限。
6. Relay UDP 不可用或所有 UDP 都失败时，自动模式选择可用的可靠媒体路径。可达的直连可靠路径也应参与选择，不必一律绕经 Relay。
7. 按现有 Client → Panel 协议报告远端接入结果。Relay socket 建立、房间创建、UDP 探测响应和本地 IPC 均不等于远端会话接入成功。
   保留 `CpTransportConnected` 的真实接入含义；首帧/媒体就绪另记状态与耗时，不能通过提前发成功事件掩盖媒体失败。

可达性失败允许试备用路径；权限拒绝、会话占用、目标身份变化、用户取消为终止条件，不能通过换路径绕过。
首批仅有公网 Relay 时，纯局域网离线部署仍可直连；自动模式不能把 Relay 存在作为直连成功的前提。

## 6. Native NAT 探测与 Relay UDP

复用 Relay 进程增加独立的 Native 探测/UDP 转发能力，不重新部署 Coturn，也不把新增能力叫作已交付的 ICE/STUN/TURN。
此处设计的是有限候选交换与双向 UDP 可达性检测；不承诺覆盖全部 NAT。

- Client 与 Render 从实际媒体 socket 向授权探测端点发包，获取该 socket 的外部映射；不能拿另一个临时 socket 的映射代替。
- 本地地址、公网 IPv6、管理员发布的映射端点、受认证观测地址作为有类型候选，经 Console 控制通道交换。
  候选绑定资源会话、目标运行时代际和探测代次，有数量/频率/有效期限制。
- 双端用受限探测窗口互发挑战和响应，只有验证到预期对端且双向可达才可提交路径。
  不因收到任意 UDP 包就更改目标地址；接口切换、NAT 映射变化后重新验证。
- 同网段优先验证本地候选；不依赖公网回环。对称 NAT、CGNAT、UDP 封禁等直接转入可用备用路径，不无限打洞。
- Relay UDP 仅接受现有授权房间协商出的绑定；限制目标、包长、速率与流量。不提供任意目的地址转发，未验证地址不得触发放大流量。
- 双端主动向 Relay 发包建立映射；Relay 维护房间的双端地址绑定和独立路径健康信息。
  端点加密的媒体载荷原样转发，Relay 不重编码、不承担第二套视频重传策略。
- Relay 额外报告 `udp_probe`、`udp_forward`、`reliable_forward` 能力及实际端点。现有公开端口只作为配置来源；不能硬编码 UDP 探测必在某个端口。
  若复用同一数字的 TCP/UDP 监听，Setup/容器端口、Windows 防火墙、健康检查均须同步覆盖，不能仅改源码。

Render 仍报告真实桌面/应用监听端点，不恢复退休端口。Native 在所有业务数据可经出站 Relay 建链时，不再强制要求公网 Render 端点。
WebRTC 仍校验其自身需要的直接可达端点，不能把 Native 候选当作网页客户端的通用解决方案。

## 7. 连接计划、状态和重连

连接计划是现有 descriptor 的明确新契约，由生产者与消费者同步更新；不保留老开发协议的隐式回退层。
字段按职责分组：

| 内容 | 必需信息 |
|---|---|
| 身份 | 现有资源会话 ID、目标设备/实例、Render 运行时代际、descriptor revision、访问角色 |
| 能力 | 业务模式、支持的可靠/数据报载体、媒体协议版本、RDP 隧道能力 |
| 策略 | 自动/仅直连/仅中继、允许的媒体降级方式 |
| 路径 | 有来源和有效期的候选、选定 Relay 身份/代际/端点/能力 |
| 关联 | 连接尝试 ID、控制绑定 ID、媒体路径代次；关联字段本身不授予访问权限 |
| 授权 | 复用现有 frontend grant 与 Relay admission 的受限字段，禁止进入日志和普通 URL 查询串 |

会话状态采用明确转换：`Authorizing → Connecting → Connected → Recovering → Connected / Failed → Closed`。
控制和媒体分别保有健康状态、路径和错误，避免“控制正常但视频已断”仍整体显示正常。

恢复规则：

1. 先验证/准备新路径，服务端提交新的绑定代次，双端确认后再撤旧路径；同一逻辑会话仍只占一个席位和一路许可。
2. 两条路径短暂重叠不产生双重输入。输入带逻辑顺序与绑定代次，服务端只执行当前绑定；鼠标移动可合并，按键/按钮抬起不能丢。
3. Native 媒体按流、编码代次、帧序号去重；切路径本身不清空解码参考。格式变化或确实无法恢复时才请求同步帧。
4. 控制彻底断开时释放暂存按键状态，阻止陈旧输入重放。可靠通道重连不得无条件重放任意业务请求。
5. 若旧连接仍可用则后台建新连接；如果已完全断开，只能给出重连结果与实际中断时间，不承诺无缝。
6. 网卡变化使受影响候选失效，自动重新取本地端点和探测映射。初始退避建议 250 ms、500 ms、1 s、2 s 封顶并带随机扰动。
7. Render 最后一个逻辑客户端离开后沿用 Console 配置的宽限期，默认 10 秒。路径切换不计作额外客户端，不重置计时来无限保活。
   恢复成功取消退出；超期已退出的应用不得假装能继续原流，需重新授权启动。RDP 保留 Windows 会话和应用。
8. 用户关闭、明确停止或权限撤销取消所有候选、重试与挂起回调；普通传输故障不得触发 RDP 注销、删用户或清理工作区应用。

Relay 排空保持已有连接，仅拒绝新接入。Relay 宕机后由 Console 在事务中为同一资源会话选择替代 Relay，更新 revision/绑定代次并通知双端。
这会重建通道和房间，不迁移 socket、不重启应用。替代节点容量不足时返回准确错误；不得私自挑一台服务器绕过授权。
旧绑定关闭回调不得关闭新绑定；Relay 重连也不能因相同 device ID 登记覆盖而误删另一条仍有效的会话。

Console 暂时不可达时允许有效的现存数据通道继续；新授权、需要重新授权的恢复与跨 Relay 重绑定失败时如实报告，不能无限延长授权。

## 8. 必须先修复的媒体问题

这些修复独立于 P2P，适用于所有 Native 桌面、GameHook 与 WebView。

1. 端到端保留预测帧、IDR、参考恢复帧及参考有效性。解码器只能在参考链确实无效、格式变更或启动未同步时重建。
   不能用 `extra="udp_synth"` 这样的调试字符串决定恢复策略，也不能把所有跳号都无条件放行。
2. RFI 按视频流、损坏参考范围和恢复代次合并；设置按 RTT 调整的有界重试与截止时间。恢复不支持或超时才升级为 IDR。
   RFI 和 IDR 进入同一个恢复决策器，避免互相触发风暴。
3. 编码帧号、传输包号、组帧序号与显示顺序各有明确用途；正常冗余包、重排、重复包、超时组帧失败分别计数。
4. 核对多帧重排窗口与解码时限，再根据抓包证据决定是否改接收队列；不能盲目增大缓存掩盖交互延迟。
5. 发包 pacing 使用异步定时/发送调度，禁止在处理接收与控制的 socket IO 线程忙等。队列有字节与时间上限。
6. 总线速预算计入视频、音频、FEC、安全封装与网络头开销；动态画面突发时依据 RTT、丢失和排队趋势降编码目标。
   多路会话共享同一出口时联合约束，不允许每路都按完整链路容量发送。
7. FEC 不能无条件通过增加冗余抵消拥塞；先控制总发送量，再在预算内调整冗余。
   已过播放期限的视频不继续堆积；丢弃参考帧后显式进入恢复状态。
8. 音频/输入/恢复控制优先于批量文件传输。可靠传输也必须有背压与分块；单条 TCP/WebSocket 内已提交字节仍有队头阻塞，优先级不能消除它。
   后续需要独立传输时，必须先实现同一授权会话的附属通道绑定，不能重复兑换一次性接入凭据。
9. MTU 扣除新增安全和 Relay 封装开销，在双端最小可用值下分片；UDP 分片不是 IP 分片。公网、VPN、IPv6 路径分别验证。

UDP 本身不提供拥塞控制，发送方需要承担这项职责；参考 [RFC 8085](https://www.rfc-editor.org/rfc/rfc8085.html)。
当前 `native_udp_media_v2_wire.md` 中历史 pacing 参数与现行多层 pacing 实现须在修复时统一，不能把启动日志中的单个速率值当成实际发送速率。

## 9. 安全载体与后续可靠 P2P

当前 Native v2 文档明确媒体内层未加密。新的公网探测、UDP Relay 与路径切换不能只增加一个可猜测房间号后原样外发媒体。
复用正常 TLS/HTTPS 授权，不恢复部署证书、产品自建 PKI 或客户端许可证。

UDP 安全封装建议验证标准 DTLS 的端点间会话模式：身份由已有受认证控制通道绑定，采用库支持的标准密钥协商/PSK 模式、重放保护和 AEAD。
Console 是授权信任方，Relay 只取得转发准入信息，不取得端点媒体密钥。不能手写加密、把永久设备密码作为媒体密钥或关闭验证。
DTLS 版本、库及跨平台能力仍需可运行原型确认；这是公开 UDP 扩展的交付前置门槛，当前没有声称已选定可用库。
DTLS 提供数据报安全，不自动提供拥塞控制、可靠传输或 NAT 打洞。协议性质参考 [RFC 9147](https://www.rfc-editor.org/rfc/rfc9147.html)。

若目标升级为“控制、文件、RDP 也经 P2P UDP”，再评估 QUIC streams + DATAGRAM 的统一载体原型。
QUIC DATAGRAM 可与可靠流共用连接但受拥塞控制；参见 [RFC 9221](https://www.rfc-editor.org/rfc/rfc9221.html)。
原型必须验证 Windows/Android 库边界、标准 TLS 身份、NAT 探测 socket 与握手的衔接、路径变化、MTU 和 FEC 开销。
不能因为选了 QUIC 就声称 NAT 穿透完成，也不能再叠加互相竞争的两个拥塞控制器。
本次主方案采用现有可靠通道加 Native 数据报，QUIC 不是首批交付的隐藏依赖；完整可靠 P2P 未验收前，RDP 仍以直连/Relay 可靠隧道交付。

NAT 候选与连通性检测可参考 [RFC 8445](https://www.rfc-editor.org/rfc/rfc8445.html) 的分层思路，但本方案不是一份符合 ICE 的实现声明。

## 10. UI 与可观测性

普通用户只有“自动（默认）/仅直连/仅中继”的连接策略；能力不支持的选项不可用并给出原因。
“仅直连”允许可达直连和打洞，但禁止 Relay 控制和媒体；“仅中继”不进行直连媒体探测。
仅直连模式下若只打通 UDP、可靠控制仍不可达，应明确失败，不能偷偷借用 Relay。
不向用户增加一排互相矛盾的 `forceTcp`、`forceRelay` 组合开关。

Client 状态详情分别显示控制/视频路径、实际 FPS、RTT、恢复次数。路径切换用非阻塞通知；初次失败在启动对话框保留步骤和准确原因。
中英文目录从第一版保持一致。示例：

- `route.udp_unreachable`：UDP 连接未成功，已切换为可靠传输 / UDP connection failed; using reliable transport.
- `route.network_changed`：网络已变化，正在重新连接 / Network changed. Reconnecting.
- `route.relay_unavailable`：中继暂不可用，正在尝试其他可用路径 / Relay unavailable. Trying another available path.
- `route.authorization_denied`：远端拒绝本次连接 / The remote host rejected this connection.

日志共用资源会话 ID、连接尝试 ID、流 ID、运行时代际与路径代次；不记录授权 token、媒体密钥或完整候选凭据。
分别记录采集/编码/发送/组帧/解码/显示速率、帧间隔 P95/P99、队列龄期、实际 wire bitrate、冗余成本、组帧失败与恢复时延。
路径事件记录起止时间、原因、候选来源、选中结果以及两个通道的状态。不能把“服务器发送成功”当作客户端收到。
跨机器时延测量需说明时钟同步误差；未同步时以各端单调时钟、往返测量和帧序号关联为准。

Console 的在线连接展示实际业务名字及路径摘要，详情承载诊断；首页仅聚合数量。
媒体恢复/短时切换不重复创建访问记录，不把恢复尝试增加到“运行中 X 路”。

## 11. 实施批次与验收门槛

| 批次 | 内容 | 完成条件 |
|---|---|---|
| U0：修复现有 UDP | 恢复语义、RFI 合并、准确统计；有界抓包确认初始损失位置 | 同一游戏/WebView 快速拖动对照；不再因有效恢复帧销毁解码器；故障恢复有界 |
| U1：可靠路径统一 | 连接计划、移除强制直连预检、自动 Direct/Relay、附属通道授权与绑定状态 | 禁止 Render 公网入站仍能经 Relay 连接桌面和应用；无重复授权、席位或实例；准确显示路径 |
| U2：可靠媒体备用与恢复 | UDP 失败自动降级、网卡变化、同会话切换、替代 Relay 重绑定 | UDP 完全封禁仍可用；明确停止不重连；宽限期与旧回调不会误关新连接 |
| U3：Native P2P 与 UDP Relay | 安全封装原型通过后加入候选交换、打洞、受权 UDP 转发、拥塞与 MTU 验证 | NAT 矩阵逐项通过；不支持的网络自动使用可靠备用路径；无未授权转发 |
| U4：RDP Relay | 原始可靠隧道、Console 分配、单前端接入与重连 | 双 NAT 仅出站网络可访问；Windows 会话/应用跨断线保留；不泄露生产 Windows 凭据 |
| U5：平台扩展 | Android 能力接入；按另外确认的范围处理网页和完整可靠 P2P | 各平台真实设备结果；不以协议定义或 Windows 结果替代验收 |

U0 不等待架构重写；U1/U2 先使已存在的 Relay 成为真正可用的备用路径。
阶段完成需明确支持矩阵；U1/U2 通过不表示 P2P、UDP Relay 或 RDP Relay 已交付。

必测场景：

- 同 LAN、不同子网、无 NAT 回环、普通家用 NAT、双 NAT/CGNAT、端口依赖映射、公网 IPv6、UDP 全封禁与 HTTPS 代理网络。
  代理网络不默认承诺可用；必须验证配置、TLS 与实际升级策略。
- 0/1/3/5% 随机丢包、突发丢包、乱序、重复包、带宽突降、MTU 受限、多路高动态画面加文件传输。
- 网卡重置、Wi-Fi 切换、休眠恢复、Relay 排空/重启、Console 短时不可用与恢复、资源授权撤销。
- 回调排队后销毁、分发中注销、回调内停机、重复启停、两条路径同时成功、旧路径关闭晚于新路径接入。
- 同会话尝试仅占一路许可，禁止第二人接管 RDP；游戏清理始终遵守私有 Job 与完整路径授权。

性能门槛要绑定测试条件：在已知可承载 1080p60 的 90→开发机路径、稳定 60 FPS 动态源下，连续 10 分钟报告全部阶段 FPS 与帧间隔分位数。
建议清洁网络目标显示均值至少 58 FPS、P99 帧间隔不超过 50 ms；这属于待实测确认的验收目标，不是已完成的性能声明。
故障注入时目标是恢复有界、队列不持续增长、无恢复请求风暴；不承诺 5% 丢包或低带宽下仍保持原始画质和 60 FPS。
