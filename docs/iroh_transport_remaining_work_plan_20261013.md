## 发现问题时的闭环

1. 保存应用源和Company同一时间段的日志、实际路径、码率与进程身份；远端先压缩再下载并校验SHA。跨机器墙钟先核对偏差，不能直接相减归因。
2. 区分源输出停顿、接收/恢复问题、资源接入拒绝、业务静态画面及测试工具期限。没有逐帧样本时不虚构P95/P99或卡顿占比。
3. 新的连接建立、异常退出或无法恢复等功能缺陷按日志定位；需要实现对比时先读本地RustDesk/Sunshine/Moonlight相关模块并记录HEAD，不凭猜测调参数。
4. 必要改动使用focused Release、显式18jobs，按影响范围运行回归；Client改动同步所有受影响development dist并核对SHA，远端基线后仅增量传输变化的运行文件。若后续需要编译，先选择可用构建环境和窗口，不在Company性能采样期间并发编译，也不自动在本机启动构建负载。
5. 用同一有界场景验证修复，重新核对清理和配置。只在新变化或失败说明有必要时重复原场景，不默认重跑全部安装/所有业务。

- Android继续排除，其仍消费的数据面保留。独立录制/播放、无关UI、网卡/饱和混传专项不是本计划前置条件。
- A项按有效证据或明确环境限制结项；B项逐项保留实际状态，不以缺环境无限延长A项，也不伪造通过。下一项是A1：Company实际身份和负载检查。
