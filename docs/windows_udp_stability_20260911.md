# Windows UDP 稳定性调试（进行中）

## 当前目标与结论

用户最新要求：优先 Windows 真实客户端画面稳定、不卡顿、不花屏；Android 最后再说。
每轮运行测试不超过 5 分钟。不能以首帧解码、合成 FEC 用例或单张截图代替流畅性验收。

Windows 新媒体路径已经接通，但截至本记录仍有间歇丢帧，**未完成稳定性验收**。

用户确认 90 上行具备 20 Mbps，允许自行测试；不能假定该链路只有 10 Mbps，也不将临时低码率作为最终修复。

## 已修改

- Windows Render 与共享 SDK 接入独立媒体核心；WS 的鉴权、控制、文件功能保持原有边界。
- 视频元数据受 FEC 保护；28 字节描述符及音频 4＋2 格式见 `native_udp_media_v2_wire.md`。
- 传输帧号与可跳号的采集/编码器时间戳分离；加入连接前的历史帧不触发参考帧失效。
- 已有有效参考帧时，丢帧后优先请求 RFI；不再把每个依赖帧直接转成受 1 秒节流限制的 IDR。
  不可安全失效时仍使用编码器侧的 IDR 回退，不放行缺参考的普通 P 帧。
- 接收端增加每 5 秒的完整帧交付数、交付间隔、恢复分片、丢失事件、RFI/IDR 和音频 PLC 统计。
  这些是传输统计，不等价于显示器实际呈现帧率；解码耗时另看 `LAT-decode`。
- 发送端增加实际 socket 发送等待与超时统计；不把异步提交数量冒充实际发送数量。
- 临时对照参数：pacing 从原 80 Mbps / 10 包一批改为 16 Mbps / 每批不超过 1 ms 的字节预算。
  这是调试参数，不是已冻结的通用产品带宽上限，不能由此宣称所有高码率场景已支持。

## 真实环境与初步证据

- 本机 `build_official/dist/px_client.exe` → `39.71.45.66:4613`，90 上由 Console 启动 `2dAdventure.exe`。
- 90 的编码持续接近 60 FPS，编码任务通常约 2 ms；实测 UDP 批次没有发送超时，等待主要为几十微秒至约 2 ms。
- 本机解码通常约 1～2 ms；快速移动鼠标时曾出现整段接收中断，同时音频出现补偿。
- 同时进行的独立 TCP 连接探测曾从数毫秒升至超过 1 秒或超时；不能把所有停顿归因于解码或 FEC 数学算法。
- 用户随后告知同时连接着向日葵，并退出该连接。退出后心跳延迟和流畅性显著改善，但仍有间歇掉帧；
  未做网络设备级验证，不能把共用带宽、编码资源竞争或出口限速中的任意一个直接宣布为唯一根因。
- 4 Mbps 短时对照脚本会在 `finally` 中按版本校验恢复原应用配置；第一次对照后已恢复 8 Mbps。
  不降低分辨率、帧率或静默永久覆盖用户配置。

## 帧率修复与独立链路核验（后续）

已确认 NVENC 初始参数为 30 FPS，但游戏 Hook 实际持续提供约 60 FPS。配置 4 Mbps 的对照也确实在编码器生效，
不是 Console 配置没有下发；不过它同样存在帧率不一致，所以不能把此前 4 Mbps 视为严格的线路流量上限。
进一步检查发现客户端工作模式发送函数已停用，不能把“游戏模式消息”直接认定为本次 60 FPS 的来源。
实际缺口是 Hook 绕过桌面采集器限帧，编码入口没有执行其声明的帧率。

本轮修复：

- 编码入口增加按屏幕维护的时间调度，声明帧率和允许编码速率使用同一个原子目标值。
- 目标变化后在编码线程重新建立该屏幕编码器，并请求 IDR；不在网络回调线程并发重建 NVENC。
- 帧率修改入口不再要求桌面采集模块存在；返回给客户端的配置、重新创建的桌面采集器使用当前目标值。
- 共享纹理必须先完成消费 / keyed-mutex 释放，再跳过不需要编码的帧；不能直接丢弃 Hook 采集回调。
  首轮尝试 `20260911-004958` 停在启动画面，不能算性能通过。最初怀疑提前跳过共享纹理导致停帧，
  但移动到 CopyTexture 之后的 `20260911-005901` 仍复现；调用栈显示编码线程空闲、Unity 等待，尚不能将根因归为限帧。
- 5 项调度单测及原有 11 项上游媒体参考测试通过；未修改 Hook DLL、WS 业务协议或网卡参数。
  原代码完整保留在 `backup/native_frame_rate_sync_20260911/`。
