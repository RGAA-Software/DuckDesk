## 1. 目标与范围裁决

用固定版本 Sunshine / Moonlight 的音视频 UDP 分包、FEC、收包恢复和发送节奏作为基准，替换当前自定义实现中的近似策略，减少传输造成的花屏、卡顿和音频中断。必须有差分测试证明行为，不以注释中的“同款”或单次画面正常作为验收。

### 1.1 本期要做

- 视频多块 RS-FEC、包序号/块序号处理、去重、乱序及整帧交付。
- 音频 RS-FEC、接收排序、恢复失败后的现有解码补偿衔接。
- 实际 UDP 出包 pacing、批量发送及必要的发送预算。
- 视频失效参考链的安全恢复：复用现有媒体恢复请求入口，必要时补齐编码器输出元信息。
- 公共实现由 Windows / Android 共用，平台差异只留在 socket、计时器和现有媒体接口边界。
- 上游基准、确定性差分测试、生命周期测试、短时真实客户端验收。

### 1.2 明确不做

- 不修改 WS 的连接、重连、控制、文件、鉴权、消息优先级或排队策略。
- 不将恢复请求迁到新的 WS 消息体系，不引入 ENet 产品控制通道。
- 不修改 Console、Auth、设备注册、应用调度、无人连接回收或实例保活。
- 不修改 SDK 的整个连接恢复流程，不借此次处理 unavailable 状态锁存、旧实例端口重试等独立问题。
- 不改 Web / RTC、Native P2P / Relay、RDP 专用通道；不做 iOS / macOS 适配。
- 不替换采集、Hook、编码器或解码器体系，不新增编码格式、屏幕功能或通道选择设置。
- 不移植 GameStream 的配对、RTSP 建会话、输入控制、应用管理；不承诺与原版 Moonlight / Sunshine 完整产品互连。
- 不新开监听端口，不更改现有地址映射、证书、安全或授权规则。

媒体故障不得被本模块升级成逻辑会话断开、控制租约释放或应用终止；已有产品行为保持不变。若这些行为妨碍验收，单独记录，不扩大本期修改范围。

## 3. 当前差距与最终处理

| 当前情况 | 本方案处理 |
|---|---|
| 单帧一个 FEC 块，大帧保护不足 | 对齐上游多块分割、块内保护与整帧提交 |
| 已删除错误的 EOF 立即清帧 | 移植上游完整乱序感知预测逻辑，而非重新加回 EOF 猜测 |
| 目前丢帧用节流 IDR 止损 | 保留安全底线，补齐可证明正确的 RFI 元信息后再启用相应恢复 |
| 反馈将缺片和恢复片混算 | 分开记录数据/校验实收、恢复、最终丢失与请求次数 |
| 5 秒自定义动态 FEC | 新主路径停用，先复现上游固定配置及其边界规则 |
| 固定 80 Mbps、逐包异步提交 | 对齐实际发送边界的节奏，记录提交队列与实际出包差异 |
| 音频主要靠排序和 PLC | 增加配套音频 FEC，保留必要的解码失败补偿 |

上游也有保护上限、预测误判和网络前提。目标是精确记录并对齐，不是承诺任意网络下永不丢帧。

## 4. 模块与依赖设计

拟建共享核心：`src/px_client_sdk/media_transport/`，独立 CMake 目标拟名 `pixels::media_transport`。名称在 P0 冻结，不能为了共享让 Render 链接整个客户端 SDK、Qt、UI 或客户端平台解码器。

```text
Render 编码帧 → 视频分块/FEC → 平台 UDP 发送器
Render Opus包 → 音频 FEC    → 平台 UDP 发送器
                                   ↓
SDK UDP 接收适配 → 按媒体流分派 → 视频队列/参考链 → 现有解码入口
                              → 音频队列/FEC    → 现有音频入口
```

共享核心的具体职责：

- `protocol`：媒体包序列化、解析、字段校验、版本和容量边界。
- `fec`：上游纠错库适配、块布局、恢复结果校验，不自行改纠错矩阵。
- `video`：帧分块、分片队列、参考链交付状态、类型化恢复请求。
- `audio`：保护组、排序、可恢复/不可恢复事件。
- `pacing`：纯时间/预算计算；实际系统调用留在平台适配。
- `stats`：每流计数和测试观测，不承担产品连接状态决策。

以上是职责边界，不要求每项增加虚接口。只为真实平台差异设置小接口；禁止服务定位器、全局可变单例和通用 `void*` 数据袋。

主要接入点：

- `src/px_render/network/udp/udp_transport.{h,cpp}`：发送/接收适配，保留现有授权绑定与监听端口。
- `src/px_client_sdk/connection/udp_direct_connection.{h,cpp}`：媒体收发适配，仍输出现有音视频帧接口。
- `src/px_render/architecture/events/render_event.h` 及相关编码输出路径：仅在必要时增加类型化的实际恢复帧信息。
- `src/px_client_sdk/cmake/`、Render 网络目标及 Android Native CMake：最小目标依赖调整。
- `src/px_deps/px_common/px_udp_protocol.h`、`px_fec.h`：逐项确认消费者后归档被替换部分；共享的绑定/语音控制内容不随视频替换误删。

## 5. 协议与算法合同

### 5.1 对齐层次

- 算法核心：同参数、同保护字节输入，分块与校验输出必须可与上游逐字节比较。
- 接收状态机：相同数据报序列、接收时间和外部事件，比较恢复帧、丢失预测、最终判丢和交付顺序。
- Pixels 适配层：保留现有媒体关联/分流边界；外层元信息允许不同，但必须列出转换规则与对应测试。
- 不宣称控制请求网络交付、整个产品时延或全部 wire 格式与原版一致。

优先保留上游媒体内层头布局、保护区间和分块语义；不再凭理解重造相似包格式。P0 必须冻结字节级协议表，明确：字节序、字段宽度、帧/包/块序号、时间戳单位、长度、填充、SOF/EOF、恢复类型、保护范围及版本。

必要的 Pixels 外层开销计入 UDP 负载预算，不能沿用上游包大小后再附加头导致超限。协议版本改变后两端同步部署，未知版本拒绝进入解码；不新增旧媒体协议运行时回退。

会话关联、端点准入、踢出和租约规则保持现状。复用关联结果只是分派媒体，不得因为照搬 GameStream 包而绕过授权。

### 5.2 视频

- 对齐单块 RS 数据＋校验上限 255，配套基线每帧最多 4 块；精确复现分割、最小校验数、填充和超大帧降级条件。
- 不采用本轮止损的“截断 parity 数量”作为最终上游算法替代品。
- 分块恢复完成不等于帧可提交；必须检查帧所需块及元信息完整性。
- 恢复生成的包不冒充网络实收包，不计入乱序历史；重复包不增加保护预算。
- 预测 RFI 必须包含上游的乱序检测、冷却及误判退出行为；预测后不清空仍可恢复的数据。
- 不额外加入自创跨帧等待窗口。下一块/下一帧到来时如何处理旧块，按固定基线执行并测试。
- 校验序号回绕、重连清理、迟到帧、多流隔离；不把任意旧关键帧当作新流标志。
- 首次解码必须有正确参考起点，不能把未恢复的参考链交给解码器掩错。

### 5.3 RFI / IDR 与 WS 边界

1. 共享核心产生类型化媒体恢复请求，复用当前媒体恢复请求入口，不改 WS 协议或控制实现。
2. RFI 区间合并、参考窗口、恢复确认按上游语义对齐；实际标记来自编码器输出，不能来自“请求已收到”。
3. 按实际参考帧容量和编码器支持情况判断；不继续用固定 16 替代真实编码器条件。
4. 请求未生效、恢复帧再次丢失、不支持 RFI、解码器要求关键帧时，走明确 IDR 回退。
5. 当前请求承载与上游可靠控制不同，不能声称端到端恢复时延完全一致。对现有请求通道的丢包进行测试，不为追求一致擅自迁移到 WS 或加入可靠 UDP 协议。
6. 若现有请求入口无法表达所需区间/确认，仅列明最小媒体协议扩展，不修改业务控制；若需要改变 WS，必须停在该边界单独说明。本期不能以假确认绕过问题。
7. 保持固定周期重试要求，不引入指数退避；上游事件合并与去重不是无限重试风暴。与基线不同的重试节奏列入适配差异表。

### 5.4 音频

- 对齐配套上游的 4 数据＋2 校验保护组及其序号、校验包、填充和恢复处理。
- 正常顺序到达的音频尽快交付，不为等完整保护组无条件增加播放延迟。
- 保护组耗尽后的缺口交给现有解码补偿，避免同一包恢复与 PLC 重复交付。
- P0 必须核对 Opus 包时长：上游 RTSP 默认包时长为 5 ms，当前 SDK 合成音频使用 20 ms；相同 4＋2 组不代表相同恢复等待时间。
- 第一版不借此重写音频采集。冻结两端一致的包时长/采样参数，并在相同参数下做算法差分；若要改现有 Opus 帧长，必须明确生产/消费端的最小改动与独立验收。
- 上行语音通话的呼叫控制、APM 和状态机不改；首期音频 FEC 对齐 Render 下行音轨，不自动扩大到语音产品重构。

### 5.5 Pacing、预算和指标

- 复制上游的批次、跨帧时间锚点和实际发送边界处理；Windows 需要审查批量发送及不支持时的逐包回退。
- 区分编码帧排队、提交 socket、系统发送完成，禁止用“提交了多少包”冒充已出包。
- 上游源码中的速率常量不是链路测速结果；基准参数和产品参数分别记录，不能无依据照搬 800 Mbps，也不能称当前 80 Mbps 已与其等价。
- 对齐上游预留 FEC、音频和协议开销的码率计算意图及实际公式；仅涉及 UDP 会话的有效编码参数，不改业务配置体系。
- 第一版停用旧 5 秒自适应 FEC，保留明确固定冗余配置。新的自适应算法不在本期。
- 队列必须有明确资源上限与可取消发送；不能无限积压。额外的排队丢帧策略若不同于上游，应列明影响并保证参考链恢复，不藏在适配层。
- 按流统计：实收数据/校验分片、重复/乱序、恢复分片、完整/不可恢复帧、预测误判、IDR/RFI 次数、队列深度、出包时间及发送错误。恢复请求次数不等于丢帧数。

## 7. 验证矩阵

### 7.1 确定性差分

固定种子、可注入时钟和可复放数据报轨迹；参考实现与移植实现采用相同功能开关。上游 Debug 的 FEC 验证模式会主动模拟丢包，不能与普通 Release 行为混作同一基准。

| 维度 | 覆盖要求 |
|---|---|
| 分块 | 单包、小帧、1–4 块、块阈值两侧、最小 parity、超大帧、最大合法长度 |
| 丢包 | 无丢包、任意单片、SOF/EOF、满校验预算、超过预算、丢整块/整帧 |
| 到达顺序 | 逆序、校验先到、EOF 先到、跨块/跨帧乱序、重复、极迟到包 |
| 参考链 | 初始 P 帧、连续失效区间、恢复请求/恢复帧丢失、无 RFI 编码器、IDR 再次丢失 |
| 音频 | 正常即时交付、保护组恢复、组边界、不可恢复缺口、PLC 去重、不同合法包长 |
| 输入校验 | 截断、错误字段组合、未知版本、长度溢出、超限块数、无效元信息 |
| 多流 | 不同会话/屏幕交错输入、重复序号、停止其中一个流不影响另一个 |

能恢复时逐字节比对；不能恢复时比较事件、交付顺序与参考链状态，不要求上游与产品日志文本一致。上游缺陷不能盲目复制，需最小安全修正、明确差异及独立测试。

### 7.2 生命周期

覆盖部分初始化失败、排队回调后析构、派发中注销、回调内停止、发送未完成时关闭、反复 Start/Stop、弱引用失效和资源清理顺序。共享核心不管理产品连接生命周期；只响应现有调用方的创建/停止/重置。

### 7.3 短时真实测试

- 每轮测试硬上限 5 分钟，不安排长时间 soak；构建耗时与运行测试计时分开记录。
- 场景：本机两个独立目录验证闭环；本机 Client → 90 Render 验证实际网络。
- 应用：90 的 `D:/software/2dadventure/2dAdventure.exe`、`D:/software/心脏医学可执行/心脏医学可执行/心脏-医学动态展示.exe`；不做中文输入专项。
- 对比前后必须保持应用、分辨率、帧率、编码格式、包时长和总预算一致；区分编码码率与带 FEC 的总带宽。
- 记录帧交付间隔、不可恢复帧、恢复耗时、音频补偿、队列长度、CPU/内存和解码错误。视频合成字节恢复不代表真实图像一定正确，需要客户端实际播放检查。
- 网络损伤先用测试代理/离线轨迹，不能通过关防火墙、改系统全局网络策略或中断 WS 制造测试条件。
- Android 无手机时仅确认构建；有 USB 时覆盖安装，不卸载、不清数据。不得把 Windows 结果当作 Android 实测。
- UDP/WS 断线联动、实例回收和控制请求可靠传输体系不作为本期新增功能；若复现独立问题，注明对媒体验收的影响。

定量性能门槛在 P0 取得上游同条件基线后冻结，不能先写未经测量的毫秒数，也不能测试后为过关放宽。硬门槛始终包括：可恢复数据一致、无损坏帧放行、无重复交付、资源有界及安全停机。
