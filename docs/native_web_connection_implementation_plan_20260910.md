# Native / Web 连接体系完善实施计划

日期：2026-09-10。状态：实施中；P2 的本机代码、单元回归、Render 构建和产物发布已完成。P3 的 IPv4 候选配置链与单元测试已完成，真实 Render 端到端验收仍按本文件矩阵执行。

## 1. 已确认的产品边界

当前目标是云电脑、云渲染应用和云游戏：Console 管理和授权，客户端访问指定 Render。
一台 Console 管理大量独立节点；Console、Render、浏览器信令服务和 RTC 转发服务不要求在同一机器。
90 当前同机部署只是联调实例，不作为产品拓扑前提。

| 客户端 | 唯一维护的业务连接体系 | 当前范围 |
|---|---|---|
| Native（Windows、Android，未来其他 Native 平台） | WS + UDP | WS 承载控制、剪贴板、文件等业务；UDP/FEC 承载音视频；直接访问 Render |
| Web | WebRTC | 保留 RTC 直连、RTC 标准两种模式；优先直连，标准模式最低优先级兜底 |

- Native 不接入或回退到 WebRTC；不在本次开发 Native 公网 P2P 打洞 / Relay。
- Web 不添加 WS / UDP 媒体回退；HTTP / WSS 信令、登录、票据接口不算另一套业务媒体通道。
- RTC 标准模式可以通过现有 Coturn 完成 TURN 转发；它不是尚未开发的 Native Relay。
- 标准模式优先级最低，不等于删除、长期禁用或不验收；最终要让其信令和 Coturn 正常工作。
- 不恢复客户端“强制选择通道”设置。测试工具可隔离验证指定模式，不作为产品用户选项。
- 所有业务连接、服务注册和可恢复传输故障均使用固定短间隔持续 retry：不得采用指数退避、随机抖动、累计次数上限或失败后自行放弃。只有用户显式断开、组件停止、会话取消或不可继续的资源清理才结束重试；每次失败先完成本次资源回收，再发起下一次尝试。
- 不以标准模式测通替代 RTC 直连修复；也不以 Native 测通替代 Web 验收。
- 旧文档中“4605 本次不开放”记录的是上一轮部署状态，不再作为禁止恢复浏览器所需信令入口的产品决定。

## 2. 已完成基础与明确缺口

- Service 已有独立节点配置、本机应用端口分配；Console 支持应用端口填 0 请求节点自动分配。
- Render RTC 媒体端口范围已有配置与参数传递基础，不重新引入全平台共享端口池。
- 90 已短时验证游戏、桌面画面、普通键鼠、双向文本剪贴板、Native 文件上传 / 下载。
- 90 的旧安装入口已清理，当前运行目录、证书和回滚位置见 [调试环境](debug_environment.md)。

### 2.2 本轮需要处理

1. 节点访问地址、协议端口映射、实例实际端点尚未形成一致的配置 / 上报 / 票据契约。
2. RTC 直连分配接口曾将访问者 `remote_address()` 传给候选地址补充逻辑；P3 已改为使用受控的 Render 通告 IPv4，仍须完成 IPv6 / 域名受控解析和真实网络验收。
3. 失败的 RTC 建连曾留下控制席位，导致后续 Native 连接被拒绝；P2 已实现失败预留的即时释放，仍需在真实 Render 上按矩阵完成端到端验证。
4. 浏览器标准模式依赖信令入口，但此前配置关闭了入口，前端仍可能根据地址 / 端口值回退。
5. Coturn 尚未完成真实转发验收；音频和录制也未在本轮环境完成验收。

以上是已观察现象和已定位代码风险，不声称候选地址是所有 RTC 失败的唯一原因。

## 3. 配置归属与最小可用模型

### 3.1 Console

只配置自身监听、外部管理 URL、Auth 接入，以及浏览器信令和共享 RTC 服务引用。

- 管理地址必须可由目标用户和节点访问；可以使用统一域名，不强制同时填写内网与公网 IP。
- 不把 Console 的地址当作 Render 地址，不让 Console 全局端口池代替各节点分配器。
- 保存节点报告的实际配置版本、访问端点、在线 / 就绪状态和失败原因。
- 区分“节点已连接 Console”“Render 已就绪”“客户端数据连接可达”。管理在线不是业务可达证明。
- 中心批量下发模板不是本次前置条件：第一版以节点 Panel UI 下发并由 Service 持久化的数据为唯一地址来源，Console 保存其回执。
  后续若增加模板下发，再定义期望版本、已应用版本及冲突处理，不能无版本地覆盖本机配置。

### 3.2 节点 Service / Render

用户最新确认：Render 安装包必须统一，普通部署只在 Panel UI 完成 Console 授权和节点公网地址配置，不编辑机器专属文件。

- Console 地址来自授权信息并保存到 Panel 设置；节点公网地址是同一页面上的可选字段。Panel 将二者随授权持续下发给 Service。
- Service 只在 Console 确认授权后将地址和节点身份一并加密持久化；重启后自行恢复，不依赖 Panel 抢先启动。
- 默认桌面业务端口 4601、本机管理端口 4603、应用池 4613–4998、Panel 管理与录像端口 4999、节点 RTC 媒体池
  5000–5031，默认内外同号。Console 托管 RTC 转发池为 5301–5428；端口池按单机实际承载能力设置，不代表软件并发上限。
  这些是可修改默认值，不是代码硬限制；局域网发现默认关闭。
- 默认值由代码补齐；完整端口表、网卡绑定和异号映射放在“高级配置”，无需复制完整示例才能启动。
- 不要求 Console 重复填写每台 Render 地址，节点自动上报。不强制填写内外网两套地址。
- UI 配置只简化应用配置，部署者仍需在网络侧放行 / 映射所用端口，并完成节点授权。
- 未配置的新安装保持明确的待授权状态，不自行猜公网入口。

`px_service.toml` 只保留安装包统一的高级端口默认值，不存 Console、节点公网地址或凭据，也不新增 node90 等机器专属部署配置。
Service 拥有节点端口资源与映射；Render 使用 Service 注入的实例配置。独立启动 Render 的入口也必须明确其生效配置。

第一版仅要求一个明确的客户端访问入口，语义如下；字段名和协议编号在实现前核对现有模型后冻结。

| 配置语义 | 规则 |
|---|---|
| 本机监听地址 | 用于绑定，不等于客户端访问地址；Service IPC 默认只绑定回环地址 |
| 节点访问主机 | IP 或域名；局域网部署可填内网地址，云端可填公网地址；不得填写 `0.0.0.0` 作为访问地址 |
| 桌面业务端口 | 固定内部端口及对外 WS、UDP 映射；不同协议分别校验 |
| 应用业务端口池 | 本机自动分配范围，以及对应的对外映射范围 / 显式条目 |
| RTC 媒体端口池 | 节点自己的内部范围，以及已配置的直接访问映射 |
| RTC 对外通告 IP | 供直接候选使用；可以与访问主机对应，但不得直接把域名字符串当作 IP 候选 |
| 配置版本 | 成功校验和应用后递增，上报 Console；失败不覆盖上一个实际可用版本 |

地址原则：

- 不根据 Service 连接 Console 时的源 IP / 源端口推断节点公开入口。
- 不直接信任客户端提交的 Host / 转发头来生成服务器候选；使用认证节点的受控配置。
- 对访问域名，Native 可正常按主机名连接；RTC 候选需显式通告 IP，或由节点在受控配置解析流程中解析和刷新。
  不在 HTTP 处理线程执行阻塞 DNS，不把访问者任意提供的域名拿来解析 / 发布。
- 保留系统产生的有效局域网候选，但本轮不建设多入口打分、跨网段策略或复杂地址自动探测系统。
- 缺少公网映射并不妨碍明确的局域网部署；公网入口则必须显式配置，不能自动猜测。

端口映射原则：

- 支持内外同号，也支持固定端口异号，以及等长连续范围映射。
- 连续映射计算：外部端口 = 外部起点 +（内部端口 − 内部起点）；检查范围长度、溢出及协议。
- 非连续映射只能使用显式条目；未实现的映射形式明确拒绝，不默认当作同号映射。
- 多台节点可使用相同内部端口；共享公网 IP 时，对外 `(主机、协议、端口)` 不得重叠。
- 应用端口必须同时满足本机可用和已声明映射可表示；不能分配成功后才随意猜一个对外端口。
- 同一节点多个 Render 的 RTC 媒体范围要协调预留 / 分配，不能各自假设独占整个池。
- 配置不会替用户创建路由器规则，也不代表运营商 / 网关端口已开放。
- 不把 90 的 IP、端口区间或设备数量写入产品限制；配置模板注释使用“管理、业务、RTC”等中性名称。

### 3.3 浏览器信令与 Coturn

- 将“浏览器信令入口”和“RTC 媒体转发服务”分开配置、检查和报告。
- Coturn 配置归其所在主机：监听 IP、公开地址 / NAT 关系、服务端口、转发端口池、凭据有效期。
- 支持 Console 托管本机 Coturn，也支持引用独立部署服务；引用远端服务不意味着 Console 能管理其本机进程。
- 信令入口也可以与 Render 分机；通过认证节点身份路由，不能允许客户端任意指定其他节点的路由身份。
- 短期访问凭据由可信后端发放；共享签名秘密、管理密码和证书私钥不下发给浏览器或所有节点。
- 标准 RTC 的信令端口不是 TURN 服务端口；打开其中一个不能替代另一个。

## 4. 工作包与实施顺序

### P1：确定并打通节点端点契约

- [ ] 盘点已有节点配置、设备桌面链接、应用启动回执、ticket、Windows / Android SDK 的端点读取位置。
- [ ] 定义强类型的节点访问配置、协议映射、实例实际端点和版本字段，不用裸数字区分消息 / 模式 / 状态。
- [ ] Service 校验配置，按本机池分配端口，启动 Render 并确认实际绑定，再计算对外端点。
- [ ] 注册 / 心跳报告节点配置与版本；实例就绪回执包含设备、实例、启动代次、实际端点及版本。
- [ ] Console 接受认证节点自己的回执，拒绝跨节点上报、旧代次回执和冲突映射。
- [ ] ticket / launch 信息下发目标 Render 的实际端点，而不是 Console 地址或未转换的内部端口。
- [ ] 更新 Windows、Android 的消费链路；WS 与 UDP 端口若不同，SDK 不再隐含“必然同号”。
- [ ] Console 管理页面显示监听 / 访问地址、映射和已应用状态；不增加客户端强制选通道开关。
- [ ] 明确修改配置时的行为：现有实例保留已确认配置，新实例使用新版本；需要迁移时先受控排空。
- [ ] 对旧设备记录做一次性明确迁移 / 重新注册，不维持两套隐式端点来源。保留备份与可回滚记录。

验收门槛：同号、异号、无效映射、端口耗尽 / 复用、迟到回执均有测试；分机部署不引用错误的 localhost。

### P2：统一失败回收，消除控制席位残留

P1 契约确定后优先完成本项，防止 Web 故障继续影响已可用的 Native。

- [x] 明确现有会话生命周期：分配、建连、已连接、关闭、已关闭；区分建连预留和已连接后的重连保留期。
- [x] 从资源预留 / 开始建连即启动有界超时；不能等数据通道打开或首个心跳后才计时。
- [x] 覆盖 SDP / ICE 失败、HTTP 应答取消、客户端关闭、数据通道未打开、超时及票据拒绝等路径。
- [x] 统一释放对应 RTC 会话、数据通道、候选资源、定时器、路由绑定和控制席位。
- [x] 关闭动作幂等，按连接 ID / 启动代次核对归属；迟到回调不得关闭已经接替的新连接。
- [x] 真实 90 验收：浏览器 RTC 分配后未形成媒体，等待 15 秒协议心跳判死后，不重启 Render 即由新的 Native 票据成功建立 WS + UDP、UI 首帧、文件通道和空闲音频授权。
- [ ] 所有失败后的下一次建连使用固定间隔持续 retry；一次性票据失效时先续期获得新票据，不以次数耗尽结束会话。
- [ ] 回调使用 weak_ptr / lock 或合规 RAII 观察方式，禁止异步捕获裸指针或 `this`。
- [ ] 与现有控制席位仲裁共用一套状态，不新增 Web 专属“强制清空所有主控”捷径。
- [ ] 保留合法的已连接会话重连宽限语义；明确失败 / 取消的建连预留不能无限续命。

验收门槛：故意造成 RTC 建连失败后，Native 可重新连接，无须重启 Render；连续失败、取消、重连不泄漏席位。
补充所有者销毁后排队回调、分发中注销、回调中 shutdown、重复 start / stop 测试。
关闭 Render / 传输不得注销 RDP 用户会话或清理工作区应用。

### P3：修复 Web RTC 直连

- [x] 分开访问者身份地址和服务器通告地址；前者继续用于认证 / 审计，不改变原 IP 绑定安全语义。
- [x] Service 从 Panel UI 下发的节点公网 IPv4 向 Render 注入通告地址；独立 Render 可在 `[rtc].advertised_ipv4` 显式设置。
- [x] 补充同端口 UDP host 候选并保留 libwebrtc 原候选；公开副本使用独立 foundation 和仅高一级优先级，避免浏览器去重或优先选择不可达私网候选；不改写 TCP / srflx 候选，不使用访问者 IP。
- [x] 覆盖空值、非法 IPv4、无候选、已有通告地址和 UDP / TCP / srflx 混合候选的单元测试。
- [ ] IPv6 和域名的受控解析 / 刷新仍待实现；不会在 HTTP 请求线程解析客户端提供的主机名。
- [ ] 建连失败交给 P2 回收；重试 / 切换使用有效票据，不复用已消费的一次性票据。
- [ ] Console 返回明确的 Web 模式可用配置；浏览器不能仅凭 `relay_host` / `relay_port` 非空认定可回退。
- [ ] 浏览器优先直连；直连成功后不并行保留另一条标准连接或额外控制席位。

验收门槛：局域网、公开 IP / 域名访问、同号 / 异号映射分别验证；实际视频解码、显示和输入均正常。
不能以 HTTP 200、收到 SDP 或建立数据通道代替出画面验收。

| 节点配置、分配、生命周期 | `rust_client/px_service/service_core/src/node_config.rs`、`rust_client/px_service/src/service_host.rs` | 扩展现有节点职责，保留已修复的进程身份检查 |
| Console 调度、端点下发 | `rust_server/px_console_server/src/app_schedule/`、`connection_ticket/`、设备与 Service 管理模块 | 根据实际回执下发目标端点 |
| 服务协议 | `src/px_deps/px_message/` 及对应 Rust 协议生成链 | 先定义字段语义，再生成；不手工修改生成代码 |
| Native 连接入口 | `src/px_client/ct_main_ws.cpp`、现有共享 Native SDK、Android 调用层 | 仅消费 WS / UDP 端点，不引入 RTC |
| 直连 HTTP / RTC | `src/px_render/network/ws/http_handler.cpp`、`network/webrtc/local/` | 地址分离、映射、异步取消与失败回收 |
| 会话归属与仲裁 | `src/px_render/session/`、RTC 两种模式生命周期 | 统一按实例 / 连接代次释放 |
| Web 启动与回退 | `web/px_console/src/user/api.ts`、`web/px_web_client/src/App.vue` | 可用性明确下发，直连优先，标准最后兜底 |
| 标准信令和 RTC 服务 | `rust_server/px_console_server/src/console_relay/`、`rtc/`、`media_sidecar.rs` | 信令与转发分工；托管 / 独立部署分开 |

上述位置为改动入口，不要求改写整个目录。实施时核对真实依赖，第三方代码保持只读。
涉及退役实现时按仓库规则完整归档到 `backup/` 后再退出活动构建；不维护可执行的旧通道兼容层。
所有新增 / 触及的项目 C++ 遵循 [所有权标准](cpp_smart_pointer_standard.md)、确定性初始化及 150 列格式限制。

## 6. 验收矩阵与当前环境使用方式

| 场景 | 必须验证 | 不能替代的验证 |
|---|---|---|
| 本机客户端 → 90 节点，CN Auth 授权 | 当前实际公网入口、Native 回归、Web 两种 RTC 模式 | 不代表 Console / Render 分机或多节点已经通过 |
| Console 与 Render 分机 | 节点注册、票据目标、信令路由、无错误 localhost | 单机切两个目录仅是辅助测试 |
| 两个独立节点 | 相同内部端口不冲突、票据不串节点、回执不串实例 | 协议 mock 通过不代表真实多机网络通过 |
| 映射边界 | 同号、异号、映射缺失、端口占用、范围耗尽 | 改数字 / 防火墙放行不代表外部网络已映射 |
| RTC 失败与模式切换 | 超时 / 取消释放席位，旧回调不影响新连接，Native 后续可用 | 重启 Render 恢复不算回收逻辑通过 |
| 独立 RTC 转发服务 | 对外候选、短期凭据、真实 relay 路径、文件内容校验 | Console 同机托管通过不等于独立部署通过 |

- 不移动现有 CN Auth 去承担其他角色；新增真实测试拓扑按已有机器条件安排，缺资源时记录未验收，不编造通过。
- 每轮功能测试最多 5 分钟，设置超时与测试进程清理；不做长时间压力 / 稳定性测试。
- 90 游戏沿用两款用户指定程序；仅通过产品启动并在私有 Job + 完整路径约束内捕获 / 回收，不接管独立启动的游戏。
- 中文输入沿用用户确认的本机通过结果，不在 90 重复开发 / 测试。
- 不记录明文密码、ticket、TURN 共享秘密或私钥；测试报告仅保留脱敏状态、错误分类、端口和必要哈希。
- 截图需确认实际 GPU 画面，而非旧连接页；输入以远端专用窗口的实际内容为证据。
- 修正自动化剪贴板保存 / 恢复，避免再次只记录 COM 异常却遗漏用户状态恢复。

## 7. 不在本次范围

- Native P2P 打洞、Native Relay、公网自动组网，以及 Native / Web 跨体系自动切换。
- iOS / macOS 平台适配；协议保持平台无关不等于这些平台已实现。
- 路由器自动配置、任意非线性 NAT 推断、复杂多入口调度、长期千台 / 万台压测。
- 改写已可用的 UDP 传输、重做所有 SDK，或把本次端点配置任务扩展为全项目能力探测重构。
- 注销 Windows 用户会话、删除工作区或接管产品未启动的游戏进程。

### 节点自动上报实现（2026-09-10）

### 节点授权恢复实现（2026-09-10）

- Service 只在 Console WebSocket 握手成功后持久化节点授权；Windows 使用当前 Service 身份的 DPAPI 加密，配置文件和普通 Service 状态文件不保存明文 appkey。
- Service 重启可优先恢复已验证授权；Panel 空授权不会清空它。不同 appkey 的新授权可以尝试，明确 401 后恢复上一次已验证授权并抑制该 appkey 的重复覆盖。
- 已验证授权本身被 Console 拒绝时，删除加密副本并等待新的有效授权，不绕过授权或以旧桌面链接降级。
- 已在 90 验收：Service 身份写入 / 读取 DPAPI 副本，停止并启动 Service 后不重新下发授权即可上线；注入无效 Panel appkey、重启 Console 强制重连后，Service 拒绝该授权并恢复已验证副本。未使用人工数据库写入。
- 仍待产品化：Panel 授权界面的失效凭据提示 / 更新流程、设备身份自动注册与轮换、跨机多节点的长期运行验收。当前实现不把旧 Panel 缓存当作可信持久来源。

### 2026-09-10 第一批实现进度

- 节点模板只保留统一端口默认值；Console 和节点公网地址由 Panel UI 随授权下发，Service 在授权成功后加密持久化。高级监听配置另见 [配置说明](node_connection_configuration.md)。

### P2 失败 RTC 回收实现（2026-09-10）

- Local RTC 从分配起计 15 秒初始建连预算：监看墙等待 ICE，其余角色等待媒体数据通道；不能建立的预留不再无限保留。
- 同步的工厂 / Peer / SDP 创建失败立即把分配返回给 HTTP 调用方；异步 SDP、ICE 终态、媒体通道关闭和心跳超时统一经幂等终止路径清理，由 sweeper 负责阻塞资源回收。
- 断开事件携带“是否曾建立媒体通道”。未建立的失败预留通过 `CloseFailedBindingById` 立即释放控制席位；已建立会话继续保留既有 5 秒重连宽限。按绑定 ID 关闭，因此迟到回调不会关闭替代连接。
- 自动化验证：`logical_session_registry`（含新增失败 RTC 预留即时释放后 Native 可马上接入的用例）与 `rtc_payload_authorization` 通过；`check_cpp_ownership` 通过；`px_render` 增量构建并发布，`px_render.exe` 和 `px_render_rtc.dll` 的 build-tree / dist SHA-256 一致。
- 尚待真实端到端验收：故意中断浏览器 RTC 的 SDP / ICE / 数据通道建连后，在不重启 Render 的前提下立即连接 Native；连续取消和重连同样不得保留席位。每轮该验证最多 5 分钟。

### P3 RTC 直连候选配置实现（2026-09-10）

- `req_ip_` 继续仅表示访问者来源；Render 不再把它写入回答 SDP。
- `px_service` 启动 Render 时，若 UI 下发的节点公网地址是 IPv4，则注入 `--rtc_advertised_ipv4`。未使用 Service 的独立 Render 可在 `settings.toml` 的 `[rtc].advertised_ipv4` 设置同一值。
- 回答 SDP 仅为 UDP `typ host` 候选添加一个同端口的通告 IPv4 副本，保留原候选、优先级和其他候选类型；配置为空或不合法时保持原 SDP，不猜测公网入口。
- 自动化验证：`rtc_candidate_sdp`、`logical_session_registry`、`rtc_payload_authorization`、`check_cpp_ownership` 与 `service_core node_config` 通过。Render / Service 已发布到 90，三个远端文件与本地产物 SHA-256 一致。
- 90 真实 Chrome 首次直连通过：`media-ready`、60 帧、远端候选 `39.71.45.66:5000/udp host`、无标准模式回退。随后两次快速重新分配均由 Render 接受并成功兑换票据，但 Chrome 诊断未取得视频统计，不能作为第二次媒体成功。
- Native 验收脚本已移除当前客户端不识别的旧 WebRTC / P2P / Relay CLI 参数；它仅按产品边界验证认证 WS + UDP。真实 `px_client.exe` 已通过 UDP 媒体、UI 首帧、文件通道和空闲音频授权。
- P2 真实验收：浏览器 RTC 分配后未形成媒体；该类已打开数据通道的非正常退出由 15 秒应用心跳判死（不是 5 秒正常重连宽限）。在该判定窗口后，用新的 Console 票据启动真实 Native 客户端，未重启 Render 即成功建立 WS + UDP、UI 首帧、文件通道和空闲音频授权。
- 后续重复浏览器诊断仍有“`RTCPeerConnection=connected` 但没有入站视频统计”的现象。公开候选已改为独立 foundation 和高一级优先级并部署到 90，但该次复测仍未形成媒体；P3 的首次直连成功保留，重复直连稳定性仍是未验收项，需从 Render 视频轨 / datachannel 建立状态继续定位，不能归因于候选地址一项后关闭问题。

后续复核发现 RTC 清理先停止信令线程、再析构需要该线程的 DataChannel，导致工作队列卡住，新会话持续等待 IDR。已修复销毁顺序，并撤回缺少依据的媒体激活判定改动。90 上同一 Render 进程连续两次 Web 直连均显示 1080p 视频、完成旧会话回收，随后真实 Native WS + UDP 首帧也通过，详见 [复核与复测记录](rtc_reassessment_20260910.md)。这关闭了本次重复直连无视频问题，不代表长期稳定性验收。

P4（标准 RTC / 转发）和 P5（多节点、独立服务）仍是未验收项。Windows 已发布并校验哈希；Android 此前编译通过，本轮没有 Android 真机测试。真实分机 / 多节点 / 独立转发服务若受环境限制尚未测到，应单列未验收项；不能把开发完成写成全场景验收完成。
